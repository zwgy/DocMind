# 历史来文批量接入简化设计

## 1. 背景与结论

现有历史来文上传需要依次创建批次、分块登记成员、提交批次，并要求调用方构造 `batch_key` 和 `name`。实际执行幂等由 `incoming_ingest_jobs` 上的 `(source_system, source_document_id)` 唯一身份保证，批次名称没有前端或业务消费者，批次状态也没有形成完整的进度闭环。

本次直接删除接入批次及批次成员概念，保留 `POST /api/incoming-documents/ingest-batches` 路径，将其改为一次登记 1 至 200 份历史来文的单阶段接口。项目仍处于开发阶段，不提供旧接口兼容、旧数据迁移或双写逻辑。

## 2. 目标

- 上传方从自身数据库读取来文元数据和长期有效附件地址，直接调用一个接口登记历史任务。
- 同一接口支持单条和批量上传；单条使用只有一个元素的 `documents` 数组。
- 网络中断或响应丢失后可原样重传，不创建重复任务。
- 历史任务登记后立即成为持久化 `pending` 任务，在历史时间窗口内由下一次 Dispatcher 扫描领取。
- 保留即时任务优先级、数据库执行令牌、租约恢复和 Worker 时间窗口复查。
- 同步修正现有上传脚本的结果误计数、请求大小分块和错误处理问题。

## 3. 非目标

- 不保留导入批次名称、批次进度、批次暂停或批次提交能力。
- 不要求上传方先生成一个包含全部历史来文的 manifest 文件。
- 不让 DocMind 连接或适配上传方数据库。
- 不在本次提供旧批次接口、数据表或数据的兼容迁移。

## 4. HTTP 契约

接口保持为：

```text
POST /api/incoming-documents/ingest-batches
```

接口继续要求管理员身份。请求示例：

```json
{
  "source_system": "oa",
  "documents": [
    {
      "source_document_id": "37908",
      "metadata": {
        "document_number": "上铁辆〔2020〕316号",
        "title": "通知",
        "incoming_date": "2020-10-20"
      },
      "files": [
        {
          "source_file_id": "202608110001",
          "filename": "来文.pdf",
          "source_url": "https://oa.example/download?id=202608110001",
          "is_main_file": true
        }
      ]
    }
  ]
}
```

`source_system` 是来文身份的一部分，必须显式提供。`metadata` 保持开放，以便后续增加业务字段；`source_document_id`、`source_file_id`、`filename`、`source_url` 和 `is_main_file` 使用固定类型。调用方不再在 `metadata` 中重复提供 `source_doc_id`，服务端在进入现有来文处理链路时生成内部兼容字段。

响应按请求顺序返回逐项结果，并附带真实汇总：

```json
{
  "items": [
    {
      "sourceDocumentId": "37908",
      "jobId": "ij_xxx",
      "status": "accepted",
      "message": null
    }
  ],
  "summary": {
    "accepted": 1,
    "exists": 0,
    "requeued": 0,
    "conflict": 0
  }
}
```

状态定义：

| 已有任务 | 输入 | 返回状态 | 数据库行为 |
| --- | --- | --- | --- |
| 不存在 | 合法 | `accepted` | 新建历史 `pending` 任务 |
| `pending/dispatching/queued/running` | 相同 | `exists` | 保持现状，不重复执行 |
| `succeeded` | 相同 | `exists` | 保持成功结果 |
| `failed/cancelled` | 相同 | `requeued` | 清理投递状态并重置为 `pending`，保留原优先级 |
| 任意状态 | 不同 | `conflict` | 不覆盖现有任务 |

若历史接口遇到既有即时任务，不得把 `priority=immediate` 降为 `historical`。需要修改失败任务的元数据或附件来源时，继续使用现有受控的任务来源刷新接口，不通过普通重传静默替换。

## 5. 校验与事务

HTTP 边界在写数据库前完成结构校验：

- `documents` 数量为 1 至 200，请求 JSON 编码后不超过 5 MiB。
- `source_system`、来文 ID、附件 ID、文件名和 URL 去除首尾空白后非空，并符合数据库字段长度。
- 同一请求内的 `source_document_id` 不得重复。
- 每份来文至少一个附件；同一来文内 `source_file_id` 唯一，最多声明一个主文件。
- 文件扩展名必须受现有来文解析器支持。
- `source_url` 必须是无内嵌用户名密码的绝对 HTTP/HTTPS URL；内网部署不增加来源主机白名单。
- `metadata.incoming_date` 存在时必须是 `YYYY-MM-DD`。

结构错误使用 422/400 拒绝整个请求，不产生部分写入。结构合法后，身份冲突作为逐项 `conflict` 返回，其他条目仍可登记；意外数据库错误回滚整次请求。

附件清单按 `source_file_id` 规范化排序后保存，因此相同附件以不同数组顺序重传仍视为相同输入。`metadata` 与规范化附件清单共同参与输入一致性比较，不新增批次键或额外客户端幂等键。

## 6. 并发与调度

仓储按 `(source_system, source_document_id)` 的稳定顺序处理身份，使用 PostgreSQL `INSERT ... ON CONFLICT DO NOTHING` 和行锁复用已有任务。稳定锁顺序避免两个包含重叠来文的批量请求以不同顺序执行时形成死锁，响应结果最终恢复为原请求顺序。

Dispatcher 的领取条件删除“存在已提交且未暂停批次”的子查询，只保留：

- 任务为 `pending` 且输入就绪；
- 已到 `next_attempt_at`；
- 即时任务全天可领取；
- 历史任务仅在配置时间窗口内可领取；
- 即时任务始终排在历史任务之前。

Worker 删除活动批次检查，但继续在下载前验证有效执行令牌和历史时间窗口。Redis 仍只保存 `job_id + delivery_token` 短消息，PostgreSQL 仍是任务事实来源。

## 7. 附件 URL 校验

平台与 DocMind 均部署在受控内网，本次不新增来源主机白名单、DNS/IP 检测或自定义重定向器。登记阶段校验 URL 是无内嵌用户名密码的绝对 HTTP/HTTPS 地址；下载继续沿用 httpx 最多五次重定向，并保留超时、100 MiB 文件上限和非文档 HTML 响应检查。

## 8. 上传脚本

`scripts/upload_incoming_batch.py` 保留为通用 HTTP 客户端示例，不负责读取业务数据库。脚本删除 `--batch-key` 和 `--name`，将输入条目转换为新接口的 `documents`。

脚本同时按 200 条和 JSON 请求体 5 MiB 两个约束分块；单条记录超过限制时在发请求前明确失败。每个请求直接登记任务，不再执行 create/items/submit。脚本必须读取逐项状态并按实际结果汇总，出现 `conflict` 时以非零退出码结束并输出对应来源 ID。传输失败可由调用方原样重跑，后端文档身份保证已提交条目不会重复创建。

脚本可继续读取 JSON 数组文件作为人工调用方式，但该文件只是客户端输入，不是服务端要求的 manifest。业务平台应分页读取自身数据库并直接构造相同请求，无需先汇总所有历史数据。

## 9. 删除范围

- 删除 `IncomingIngestBatch`、`IncomingIngestBatchItem` 模型及测试。
- 删除批次创建、成员登记、提交、暂停、恢复和列表仓储方法。
- 删除 `GET /ingest-batches`、`POST /ingest-batches/{batch_id}/items`、`submit`、`pause` 路由。
- 保留并重写 `POST /ingest-batches`。
- 保留任务列表、提优先级、失败重试和来源刷新接口。
- 删除 Dispatcher/Worker 的活动批次依赖。
- 更新架构文档、来文接入指南、环境变量模板和 changelog。

## 10. 验收标准

- 一条和 200 条来文均可通过同一接口登记，空数组、201 条和超过 5 MiB 请求被拒绝。
- 相同请求重复发送只产生一个任务；模拟“服务端已提交但响应丢失”后重传仍返回同一 `jobId`。
- 失败或取消任务以相同输入重传后重新进入 `pending`；成功任务不重新执行；不同输入返回 `conflict`。
- 两个反序重叠批量请求在真实 PostgreSQL 下无死锁、无唯一键异常、无重复任务。
- 历史接口不会降低即时任务优先级。
- 历史任务窗口内在下一次 Dispatcher 扫描时可领取，窗口外不领取；排队后越窗的旧消息被 Worker 拒绝。
- 不再存在对接入批次表、批次键或批次名称的运行时引用。
- 非 HTTP/HTTPS、带用户名密码 URL 被拒绝；合法内网地址及重定向可正常下载。
- 上传脚本按数量和字节大小正确分块，按服务端逐项结果统计，并可安全重跑。
