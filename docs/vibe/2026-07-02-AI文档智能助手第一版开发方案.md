# AI文档智能助手第一版开发方案

日期：2026-07-02  
状态：开发规格  
项目：`chat-iframe`

## 1. 目标

第一版建设一个可独立嵌入生产系统的 docMind AI 文档智能助手。生产系统页面打开助手后，助手自动接收页面内容和附件列表，匹配 docMind 已采集的来文文档，展示文档结构化抽取结果，并支持用户继续围绕页面、附件和普通聊天进行追问。

核心交付：

- 根目录新增 `chat-iframe` 项目，与 `web` 平级。
- `chat-iframe` 产出可被生产系统 iframe 嵌入的独立前端页面。
- 生产系统通过父页面脚本挂载助手，并向 iframe 传递页面内容和附件信息。
- 助手与 docMind 后端直接通讯，完成聊天和来文抽取结果查询。
- 补齐生产系统来文推送接入、文件保存、Markdown 解析、业务结构化抽取和结果存储。
- 助手打开时自动展示已匹配附件的结构化抽取结果。

## 2. 第一版范围

### 2.1 文档采集解析抽取链路

第一版文档处理链路围绕 `KnowledgeFile` 文件记录和解析后的 Markdown 展开：

```text
生产系统来文文档
  -> 生产系统推送接口
  -> docMind 文件存储与 KnowledgeFile 记录
  -> Markdown 解析
  -> 业务结构化抽取
  -> 抽取结果存储
  -> chat-iframe 查询展示
```

业务抽取输入源为 Markdown 内容，抽取结果直接服务助手展示。

生产系统来文推送接入、Markdown 解析和业务抽取属于第一版后端开发范围。`backend/package/yuxi/knowledge/extraction` 中已有分类、schema、prompt 和结果表雏形，本次开发需要补齐推送入库、解析后自动抽取、结果查询聚合和任务状态流转。

该后端链路是 `chat-iframe` 展示结构化结果的前置能力。前端开发可先基于 `/api/incoming-documents/extractions/query` 的约定响应并行推进，后端完成后替换为真实接口联调。

### 2.2 结构化抽取生效阶段

结构化抽取在 Markdown 解析成功后生效，对应 `KnowledgeFile.status = parsed` 且 `KnowledgeFile.markdown_file` 已写入。

当前 Yuxi 知识库构建过程分为：

```text
添加文件记录 uploaded
  -> 解析文件 parsing
  -> 生成 Markdown parsed
  -> 分块和向量入库 indexing/indexed
  -> 知识图谱构建 graph indexed
```

AI 文档智能助手第一版使用解析后的完整 Markdown 做业务结构化抽取，因此触发点放在 `parsed` 阶段：

- 文件记录刚创建时还没有文本内容，不能抽取。
- Markdown 解析完成后已经有完整文本，具备抽取条件。
- 向量入库阶段才会生成 `KnowledgeChunk` 和向量索引，属于 RAG 检索链路。
- 知识图谱构建依赖已入库 chunk，属于图谱检索链路。
- 结构化抽取结果直接服务助手展示，和向量检索、知识图谱构建解耦。

调用位置：

- 解析编排层调用 `knowledge_base.parse_file(...)` 成功并确认写入 `markdown_file` 后，提交业务抽取后台任务。
- `knowledge_base.parse_file(...)` 保持“只负责解析 Markdown”的底层职责，不直接耦合业务抽取。
- 批量解析、待解析文档解析、生产系统推送入库解析成功后走同一触发逻辑。
- 自动入库开启时，解析成功后先提交业务抽取任务，再继续执行向量入库；抽取失败不影响文档入库。
- 文件重新解析并生成新的 `markdown_file` 后，生成新的抽取任务；查询接口返回最新成功结果或当前运行状态。

任务执行方式：

- 结构化抽取通过 Yuxi 现有 `tasker` 任务队列异步执行，任务类型建议为 `knowledge_business_extraction`。
- 解析流程只负责提交抽取任务，不同步等待 LLM 抽取完成。
- 使用 `enqueue_unique_by_payload` 按 `kb_id + file_id + markdown_file + model_spec` 对 pending/running 任务去重。
- `tasker` 负责任务排队、进度、取消和系统任务可视化；`knowledge_business_extraction_runs/results/items` 负责保存业务抽取历史和结果。
- 助手查询接口优先返回最新成功结果；只有正在抽取且没有可展示结果时返回 `running`。

抽取分块与 `chunk_id` 处理：

- `KnowledgeChunk` 是知识库向量入库阶段的持久化分块，不作为第一版结构化抽取的前置条件。
- 结构化抽取任务读取 Markdown 后在内存中切分为抽取片段；这些片段只服务本次抽取，不写入 `knowledge_chunks`。
- `knowledge_business_extraction_items.chunk_id` 保留为可选关联字段，用于后续把结构化明细关联到已经入库的知识库 chunk。
- 第一版 Markdown 阶段抽取出的结构化明细不填 `chunk_id`，依靠 `file_id`、`source_quote` 和可选原文位置信息追溯原文。
- 后续需要把抽取结果和知识库 chunk 对齐时，可在向量入库完成后按 `source_quote` 或原文位置做补关联。

### 2.3 助手能力

`chat-iframe` 第一版提供：

- 新增聊天。
- 对话列表。
- 聊天记录。
- 流式回答展示。
- 工具调用信息展示。
- “您可以这样问我”推荐问题。
- 模型选择。
- 输入框添加附件。
- “问网页”开关，默认开启。
- “问文件”开关，默认开启。
- 页面附件列表展示与选择。
- 多附件默认选择第一个附件。
- 打开助手时自动匹配附件并展示结构化抽取结果。

### 2.4 对外形态

生产系统通过静态父页面脚本接入：

```html
<script src="https://docmind.example.com/chat-iframe/docmind-chat-iframe-parent.js"></script>
<script>
  const chat = new DocMindChatIframe({
    iframeSrc: 'https://docmind.example.com/chat-iframe/',
    user: '当前用户ID',
    initialState: 'minimized'
  })

  chat.setPageContent({
    title: document.title,
    html: document.documentElement.outerHTML,
    url: location.href
  })

  chat.setFiles([
    {
      id: '202606100417',
      name: '来文文件名.docx',
      sourceUrl: 'http://ip/xxx/default.ashx?202606100417',
      sourceKey: '202606100417',
      sizeText: '123 KB',
      selected: true
    }
  ])
</script>
```

生产系统具备显式传参能力时，优先调用 `setPageContent()` 和 `setFiles()`。生产系统仅完成脚本嵌入时，父页面脚本使用通用 DOM 规则采集页面正文和附件列表。

```text

  ├─ 父子页面通信适配
  ├─ docMind 后端 API 适配
  ├─ 附件匹配状态展示
  └─ 结构化抽取结果展示

docMind backend
  ├─ 数据采集与文件记录
  ├─ Markdown 解析
```

`chat-iframe` 独立构建和部署。iframe 嵌入、父页面通信、页面内容传递、文件列表传递、悬浮图标和窗口控制参考 `D:\work\ai-chat-iframe` 的实现方式；聊天业务逻辑复用 `web` 中已有聊天交互、状态管理和 API 约定，并按 iframe 场景裁剪实现。现有能力不满足 iframe 场景时，在 `chat-iframe` 内补充适配。

### 3.1 既有能力复用边界

`chat-iframe` 复用两类既有能力：

- 嵌入壳层参考 `ai-chat-iframe`：父页面脚本、悬浮按钮、最小化/恢复/最大化/关闭状态、`IFRAME_READY`、`REQUEST_PAGE_CONTENT`、`REQUEST_FILE_LIST`、`PAGE_FILES_UPDATED`、`INIT_CONFIG`、事件回调和 `setFiles()` / `setPageContent()`。
- 聊天业务参考 `web`：`threadApi`、`agentApi`、`chatThreads` store、消息渲染、工具调用展示、模型选择、附件上传、输入框交互和会话列表。

实现方式：

- `chat-iframe` 保持独立项目和独立构建产物。
- 组件优先抽取 `web` 中可直接复用的输入框、消息、工具调用和附件组件。
- `web/src/components/AgentChatComponent.vue` 体量较大，作为流程参考；iframe 页面实现轻量容器，避免把主站页面整体搬入 iframe。
- `ai-chat-iframe` 中页面附件 URL 上传链路替换为 docMind 的来文抽取结果查询和现有聊天接口。

### 5.5 附件 DOM 识别

生产系统附件示例：

```html
<div class="items">
  <div class="item" id="xxx_BOX" attachment="xxx">
    <a href="###" onclick="YZSoft.File.download('http://10.132.235.62:8082/YZSoft/Attachment/dafault.ashx?xxx')">
      <span class="flag"></span>
      "新车函（2026）162号.pdf"
      <span class="size">-200.16KB</span>
    </a>
  </div>
</div>
```

父页面脚本采集规则：

1. 优先扫描 `.items .item[attachment] a`，再降级扫描页面中的 `a` 元素。
2. 从 `textContent` 中移除 `.size` 文本，去掉外层引号，得到文件名。
3. 从 `.size` 或完整文本中提取大小，支持 `-200.16KB` 这类无空格格式。
4. 从 `onclick="YZSoft.File.download('...')"`、普通 `onclick` 和 `href` 中提取 URL。
5. 按 `attachment` 属性、`id` 去掉 `_BOX` 后缀、URL query、路径片段的顺序提取 `sourceKey`。
6. 文件名后缀命中文档扩展名时加入附件列表。
7. 第一个附件标记为默认选中。

支持扩展名：

```text
doc, docx, pdf, xls, xlsx, ppt, pptx, txt, md, csv
```

## 6. 父子页面通信协议

### 6.1 父页面发送给 iframe

```ts
type ParentToIframeMessage =
  | {
      type: 'INIT_CONFIG'
      payload: {
        user?: string
        token?: string
        includePageContent?: boolean
        includeFiles?: boolean
        selectedFileIds?: string[]
      }
    }
  | {
      type: 'PAGE_CONTENT'
      payload: PageContent
    }
  | {
      type: 'FILE_LIST'
      payload: IncomingPageFile[]
    }
  | {
      type: 'PAGE_FILES_UPDATED'
      payload: IncomingPageFile[]
    }
  | {
      type: 'WINDOW_STATE'
      payload: {
        state: 'minimized' | 'normal' | 'maximized' | 'closed'
      }
    }
```

`PAGE_FILES_UPDATED` 是附件列表更新的主消息；`FILE_LIST` 作为兼容别名处理。

### 6.2 iframe 发送给父页面

```ts
type IframeToParentMessage =
  | { type: 'IFRAME_READY' }
  | { type: 'REQUEST_PAGE_CONTENT' }
  | { type: 'REQUEST_FILE_LIST' }
  | { type: 'MINIMIZE' }
  | { type: 'MAXIMIZE' }
  | { type: 'RESTORE' }
  | { type: 'CLOSE' }
  | {
      type: 'CONVERSATION_CREATED'
      payload: { conversationId: string }
    }
  | {
      type: 'MESSAGE_SENT'
      payload: { conversationId: string; messageId?: string }
    }
```

`CONVERSATION_CREATED` 和 `MESSAGE_SENT` 仅作为可选通知事件，阶段八聊天能力接入后发送；iframe 嵌入、窗口控制、页面内容和附件传递不依赖这两个事件。

### 6.3 页面内容对象

```ts
type PageContent = {
  title?: string
  url?: string
  html?: string
  text?: string
}
```

### 6.4 附件对象

```ts
type IncomingPageFile = {
  id: string
  name: string
  sizeText?: string
  sizeBytes?: number
  url?: string
  sourceUrl?: string
  sourceKey?: string
  onclick?: string
  type?: 'document' | 'image' | 'unknown'

```

`url` 兼容 `ai-chat-iframe` 的文件字段；进入后端前统一归一化为 `sourceUrl`。

## 7. 助手页面流程

### 7.1 初始化

1. iframe 页面加载。
2. iframe 发送 `IFRAME_READY`。
3. 父页面发送 `INIT_CONFIG`、`PAGE_CONTENT`、`PAGE_FILES_UPDATED`。
4. iframe 初始化聊天状态。
5. “问网页”和“问文件”默认开启。
6. 页面附件默认选择第一个。
7. iframe 调用来文抽取结果查询接口。
8. 接口返回附件匹配状态和抽取结果状态。
9. 解析结果展示到聊天列表。

### 7.2 用户提问

用户发送消息时，`chat-iframe` 组装以下上下文：

- 用户输入。
- 当前模型。
- 当前会话 ID。
- “问网页”开关状态。
- 页面内容摘要或 Markdown 文本。
- “问文件”开关状态。
- 选中附件的 `kbId/fileId`、匹配状态和抽取摘要。
- 用户手动添加的附件。

聊天接口沿用 docMind 后端现有流式聊天能力。接口适配层放在 `chat-iframe/src/apis/chat.ts`。

### 7.3 结构化结果展示

结构化结果作为聊天列表中的助手消息或固定结果卡片展示：

```text
已识别来文：来文文件名.docx

文档分类：
- 风险管理类
- 阶段性工作类

风险事项：
- 现场作业监护需加强

任务要求：
- 加强现场监护

原文依据：
「现场作业监护需加强，应完善现场监护要求」
```

展示策略：

- 同一会话、同一文件维护一条结构化结果消息。
- 附件切换后刷新当前文件的结果展示。
- 抽取状态变化后更新原消息。
- 结果写入聊天记录，支持再次打开历史会话查看。

## 8. 后端数据链路

### 8.1 推送入库

生产系统调用推送接口写入 `KnowledgeFile` 时同步来源信息：

```json
{
  "source_system": "production",
  "source_url": "http://ip/xxx/default.ashx?202606100417",
  "source_key": "202606100417",
  "source_filename": "来文文件名.docx",
  "source_size_text": "123 KB"
}
```

来源信息第一版存入 `KnowledgeFile.processing_params`。

### 8.2 Markdown 解析

文档保存后执行现有解析流程，解析结果写入：

```text
KnowledgeFile.markdown_file
KnowledgeFile.status = parsed
```

`KnowledgeFile.markdown_file` 存储解析后 Markdown 文件的 MinIO 地址。解析流程会把完整 Markdown 文本保存为 `{kb_id}/parsed/{file_id}.md`，再把上传结果地址写入该字段。业务抽取读取该字段指向的 Markdown 文件内容作为输入。

### 8.3 业务结构化抽取

Markdown 解析完成后提交业务抽取任务。抽取服务读取 `KnowledgeFile.markdown_file` 内容，根据 `backend/package/yuxi/knowledge/extraction/schemas.py` 中定义的分类和字段结构生成结果。

结果写入：

```text
knowledge_business_extraction_runs
knowledge_business_extraction_results
knowledge_business_extraction_items
```

三张表的业务含义：

| 表 | 含义 | 示例 |
| --- | --- | --- |
| `knowledge_business_extraction_runs` | 一次抽取任务的执行记录 | “2026-07-02 14:00 用 Qwen 对 file_001 抽取了一次，执行成功/失败” |
| `knowledge_business_extraction_results` | 这次抽取对整份文件的分类结果 | “这份文档命中风险管理类、阶段性工作类，需要抽取风险事项和任务要求” |
| `knowledge_business_extraction_items` | 从文档里抽出来的一条条结构化明细 | “风险事项：现场作业监护需加强；任务要求：完善现场监护要求” |

后文中的 `run/result/item` 分别对应“抽取任务 / 文件级结果 / 结构化明细”。

抽取状态用于助手展示：

```text
ready
running
not_found
failed
```

### 8.4 现有抽取基线

现有结构化抽取代码已经具备：

- `schemas.py`：文档分类、分类到抽取 schema 的映射、风险/任务/考评/奖惩/管理要求条目结构。
- `prompts.py`：分类 prompt 和结构化抽取 prompt。
- `llm.py` / `json_utils.py`：模型 JSON 输出调用与解析。
- `service.py`：可以对已有文本片段做分类、选择抽取 schema、抽取结构化明细，并写入抽取任务/文件级结果/结构化明细三类数据。
- `KnowledgeBusinessExtractionRepository`：可以创建抽取任务、更新任务状态、替换抽取结果、按文件查询最新结果、确认条目。
- `knowledge_business_extraction_runs/results/items`：已经具备抽取任务、文件级分类结果、结构化明细的存储结构。

当前缺口和第一版需要补齐的内容：

- 现有抽取服务主要吃 `KnowledgeChunk`，而 `KnowledgeChunk` 在向量入库阶段才生成；第一版要增加“读取解析后 Markdown 文件并切分”的入口。
- 现有抽取服务需要手动调用，第一版要在 Markdown 解析成功后自动提交抽取任务。
- 现有仓库能按 `file_id` 查结果，第一版要支持“页面附件信息 -> docMind 文件 -> 最新抽取结果”的完整查询。
- 现有数据库状态是后端内部状态，第一版要翻译成前端容易展示的 `ready/running/not_found/failed`。
- 同一文件、同一 Markdown、同一模型已经有成功抽取结果时，第一版要复用结果，避免反复抽取。
- Markdown 阶段抽取时还没有 `KnowledgeChunk` 记录，结构化明细不填 `chunk_id`，依靠 `source_quote` 和可选位置信息追溯原文。
- 测试要覆盖 Markdown 输入、自动触发、查询聚合、状态翻译和失败场景。

## 9. 后端接口

### 9.1 查询来文抽取结果

`POST /api/incoming-documents/extractions/query`

请求：

```json
{
  "files": [
    {
      "id": "202606100417",
      "name": "来文文件名.docx",
      "sizeText": "123 KB",
      "sizeBytes": 125952,
      "sourceUrl": "http://ip/xxx/default.ashx?202606100417",
      "sourceKey": "202606100417",
      "onclick": "xxx"
    }
  ]
}
```

响应：

```json
{
  "items": [
    {
      "incomingFileId": "202606100417",
      "name": "来文文件名.docx",
      "matchStatus": "matched",
      "kbId": "kb_xxx",
      "fileId": "file_xxx",
      "extractionStatus": "ready",
      "runId": "ber_xxx",
      "categories": {},
      "items": [],
      "reason": "source_key matched"
    }
  ]
}
```

接口内部流程：

1. 标准化页面附件信息。
2. 根据 `sourceKey/sourceUrl/filename/fileSize` 匹配 `KnowledgeFile`。
3. 匹配成功后查询最新业务抽取结果。
4. 组装匹配状态、抽取状态和结构化结果。

匹配状态：

```ts
type IncomingDocumentMatchStatus =
  | 'matched'
  | 'multiple'
  | 'pending_sync'
  | 'not_found'
```

匹配优先级：

```text
source_key/source_url 精确匹配
  -> source_doc_id + filename
  -> filename + file_size
  -> filename
```

抽取状态：

```ts
type IncomingDocumentExtractionStatus =
  | 'ready'
  | 'running'
  | 'not_found'
  | 'failed'
```

状态翻译规则：

后端内部会同时判断两件事：

- 页面附件有没有匹配到 docMind 文件，返回 `matchStatus`。
- 匹配到文件后有没有可展示的抽取结果，返回 `extractionStatus`。

前端只使用这两个状态展示文案，不直接展示数据库里的任务状态。

| 条件 | `matchStatus` | `extractionStatus` |
| --- | --- | --- |
| 页面附件匹配到唯一 `KnowledgeFile`，并且已有可展示抽取结果 | `matched` | `ready` |
| 页面附件匹配到唯一 `KnowledgeFile`，抽取任务正在执行 | `matched` | `running` |
| 页面附件匹配到唯一 `KnowledgeFile`，但还没有抽取结果 | `matched` | `not_found` |
| 页面附件匹配到唯一 `KnowledgeFile`，但最近一次抽取失败 | `matched` | `failed` |
| 页面附件命中多份 `KnowledgeFile` | `multiple` | `not_found` |
| 页面附件带来源线索但未匹配到 `KnowledgeFile` | `pending_sync` | `not_found` |
| 页面附件缺少有效来源线索且未匹配 | `not_found` | `not_found` |

`KnowledgeBusinessExtractionResult.status = draft` 表示“自动抽取生成的未人工确认结果”。第一版助手页面只读展示该结果，因此接口返回 `extractionStatus = ready`。

## 10. 后端开发点

### 10.1 推送入库与解析任务

补齐生产系统来文推送入库任务：

- 接收生产系统推送的来文文档文件或下载链接。
- 保存原始文件，创建或更新 `KnowledgeFile`。
- 写入 `processing_params.source_system/source_url/source_key/source_filename/source_size_text`。
- 调用现有文档解析流程生成 Markdown。
- Markdown 解析成功后提交业务结构化抽取任务，触发点为 `parsed` 阶段。
- 记录采集、解析、抽取状态，供查询接口返回 `running/not_found/failed`。

### 10.2 Repository

扩展 `KnowledgeFileRepository`：

- 按 `processing_params.source_key` 查询。
- 按 `processing_params.source_url` 查询。
- 按 `filename + file_size` 查询。
- 按 `filename` 查询候选文件。

扩展 `KnowledgeBusinessExtractionRepository`：

- 按 `file_id` 查询最新抽取任务。
- 返回抽取任务、文件级结果、结构化明细的聚合视图。
- 返回抽取状态和失败原因。
- 支持按 `file_id + markdown_file + model_spec` 判断是否已有可复用成功结果。

### 10.3 Service

新增：

```text
backend/package/yuxi/services/incoming_document_service.py
```

职责：

- 标准化 `IncomingPageFile`。
- 兼容页面文件字段 `url` 和 `sourceUrl`。
- 生成稳定 `incomingFileId`。
- 执行附件匹配优先级，作为查询接口的内部步骤。
- 组装匹配状态、抽取状态和抽取结果查询响应。
- 生成前端展示摘要。

扩展：

```text
backend/package/yuxi/knowledge/extraction/service.py
```

能力：

- 从 `KnowledgeFile.markdown_file` 读取 Markdown。
- 以 Markdown 内容作为业务抽取输入。
- 按文档长度决定抽取片段：短文档可作为一个片段，长文档使用现有 `chunk_markdown` 能力在内存中切分。
- 抽取入口不依赖 `KnowledgeChunk` 已写入数据库。
- Markdown 阶段生成的内存片段不写入 `knowledge_chunks`，结构化明细写库时 `chunk_id` 为空。
- 复用现有分类、schema、LLM 调用和结果入库逻辑。
- 记录 `markdown_file`、`model_spec`、片段数量和错误摘要到 `run_metadata`。
- 在解析成功后由后台任务触发。

## 13. 安全与权限

1. 后端接口校验登录态或可信嵌入 token。
2. 匹配和抽取查询只返回当前用户有权限访问的文件。
3. 父页面传入的 HTML、URL、onclick 作为文本处理。
4. 父页面脚本发送 postMessage 时使用 `targetOrigin`，iframe 接收消息时校验 `originAllowlist`。
5. `token` 支持传入 docMind 登录 token 或短期签名嵌入 token，`chat-iframe` API 请求统一携带认证信息。
6. `chat-iframe` 独立部署时，后端通过 `Content-Security-Policy: frame-ancestors ...` 允许被生产系统域名 iframe 嵌入。
7. 使用 Cookie 登录态时，部署需配置跨站 iframe 可用的 Cookie 策略。
8. 页面展示文件名、大小、匹配状态和抽取摘要。

## 14. 验收标准

### 14.1 嵌入

- 生产系统页面通过 `docmind-chat-iframe-parent.js` 打开助手。
- 助手支持最小化、恢复、最大化、关闭。
- iframe 页面可独立构建和部署。
- 父页面可通过 `setPageContent()` 和 `setFiles()` 显式传递上下文。
- 父页面脚本可从示例附件 DOM 中识别文件名、大小、来源 URL 和 `sourceKey`。

### 14.2 聊天

- 支持新增聊天、对话列表、聊天记录。
- 支持流式回答和工具调用展示。
- 支持“您可以这样问我”。
- 支持模型选择。
- 支持输入框添加附件。
- 支持“问网页”和“问文件”开关。
- 普通聊天、页面问答、文件问答均可发送消息。

### 14.3 文档抽取结果展示

- 助手打开后自动调用来文抽取结果查询接口。
- 多附件默认选中第一个。
- 接口返回附件匹配状态和抽取结果状态。
- `ready` 状态展示结构化结果。
- `running` 状态展示进度文案。
- `pending_sync`、`not_found`、`multiple` 状态展示清晰提示。
- 结构化结果写入聊天记录或会话持久化消息。

### 14.4 数据链路

- 采集入库时保存生产系统来源元数据。
- Markdown 解析成功后自动触发业务抽取。
- 业务抽取结果写入现有抽取结果表。
- 抽取结果查询接口可按页面附件信息批量返回。
