# 来文管理与知识库解耦设计方案

> **For agentic workers:** 本文档是实施前设计方案。实现时以“来文处理独立于知识库，人工触发后复用知识库入库链路”为核心约束，不保留 `INCOMING_DEFAULT_KB_ID` 默认知识库入库逻辑。

## 0. 2026-07-08 修订：业务结构化抽取独立边界

业务结构化抽取是独立能力，不属于来文系统，也不属于知识库系统。来文和知识库即使没有业务结构化抽取，也必须能独立完成各自核心流程：

- 来文系统负责：保存原文、解析 Markdown、生成 chat-iframe 摘要、展示来文管理列表与详情。
- 知识库系统负责：保存知识库文件、解析、分块、embedding、写入向量库、检索问答。
- 业务结构化抽取负责：基于 Markdown 做业务分类、schema 选择和结构化条目抽取。

固定调用规则：

1. 来文解析出 Markdown 后调用业务结构化抽取模块，并保存抽取结果。
2. “从来文存入知识库”只执行知识库入库链路；如果来文已有业务抽取结果，则在入库成功后关联 `kb_id/file_id`，不重复抽取。
3. “直接上传到知识库”的文件不自动执行业务结构化抽取。
4. “从来文存入知识库”时如果没有业务抽取结果，也不补抽；业务抽取失败不能阻断知识库入库。

命名与数据模型同步调整：

- 删除 `IncomingDocumentExtractionRun`，来文摘要状态继续写在 `incoming_documents`。
- 将 `KnowledgeBusinessExtractionRun/Result/Item` 改为 `DocumentBusinessExtractionRun/Result/Item`。
- 将 `knowledge_business_extraction_runs/results/items` 改为 `document_business_extraction_runs/results/items`。
- 将 `KnowledgeBusinessExtractionRepository` 改为 `DocumentBusinessExtractionRepository`。
- 将 `backend/package/yuxi/knowledge/extraction` 下的业务抽取实现迁移到独立模块 `backend/package/yuxi/document_extraction`。

本文档下方旧章节中如果仍出现“知识库业务抽取”“incoming_document_extraction_runs”或“知识库入库后自动业务抽取”的表述，以本修订为准；实施阶段应同步删除旧逻辑和旧命名，不为未上线代码保留兼容分支。

## 1. 背景

当前 `/incoming-documents` 接口把外部系统上传的来文直接绑定到默认知识库，后端依赖 `INCOMING_DEFAULT_KB_ID`。这会带来三个问题：

1. 来文处理和知识库入库耦合，外部系统只是想上传附件并生成摘要时，也必须配置知识库。
2. 所有来文都进入同一个知识库，后续按业务分类建设多个知识库时会污染检索范围。
3. chat-iframe 需要的是“当前来文摘要和必要时读取全文”的上下文能力，不等同于所有来文都必须完成 embedding 和向量索引。

涉及历史改动主要包括：

- `9ab2488099483034096c89cae475cdaa53e93a3f`：新增知识库业务结构化抽取能力。
- `218050a9612866030214b7cd27bd9072962b2932`：补齐来文智能助手后端闭环，并引入默认知识库入库逻辑。

本功能尚未正式上线，可以大幅调整现有来文逻辑，不需要为了兼容保留错误边界。

## 2. 目标

1. 外部系统上传来文后，docMind 保存原文、解析文本、分类、摘要和结构化抽取结果。
2. 来文默认不进入知识库，chat-iframe 仍可查询摘要并在需要时读取完整解析文本。
3. Web 新增“来文管理”，管理员可查看来文、原文、摘要、分类和处理状态。
4. 管理员在“来文管理”中手动选择目标知识库并点击“存入知识库”后，系统自动完成知识库添加、解析、切片、embedding、索引。
5. Web 端复用 docMind 现有设计语言和已有知识库参数组件，不重新做一套上传/入库 UI。
6. 后端复用现有知识库入库核心流程，不复制一套“来文专用解析索引流程”。

## 3. 非目标

1. v1 不做分类自动入库。分类只作为管理参考，不自动决定知识库。
2. v1 不做普通用户隔离。“来文管理”仅管理员可见。
3. v1 不做来文版本历史。相同外部来源的内容变更会覆盖当前记录并重新处理。
4. v1 不做自动清理或物理删除。保留归档扩展点，但不实现归档/删除入口。
5. v1 不复用来文解析出的 markdown 直接跳过知识库解析。入知识库时走现有知识库解析和索引链路，确保知识库文件状态、预览、切片和索引行为一致。
6. v1 不新增独立 Agent 工具读取 MinIO 来文。chat-iframe 需要全文时，后端把解析 markdown 临时写入当前会话 sandbox，再使用现有 `read_file`。

## 4. 固定设计决策

### 4.1 存储

来文长期存储使用 MinIO + PostgreSQL：

- 原始文件保存到 MinIO。
- 解析后的 markdown 保存到 MinIO。
- 来文元数据、分类、摘要、结构化抽取结果保存到 PostgreSQL。
- sandbox 只用于 chat-iframe 单次会话运行时临时读取全文，不作为长期存储。

### 4.2 分类与摘要

每个来文只有一个主分类结果，但可以保存多类摘要/抽取信息：

- `classification`：主分类，例如合同、客户审查、业务申请、其他。
- `summary`：完整附件摘要，用于 chat-iframe 快速理解来文。
- `structured_result`：结构化字段和多种摘要信息，例如风险点、主体信息、金额、日期、待办事项。

分类和摘要基于解析后的 markdown。短文档一次调用模型；长文档按 chunk 先分段摘要，再合并为总摘要和结构化结果。

### 4.3 chat-iframe 读取策略

chat-iframe 不依赖知识库也能使用来文：

1. 前端通过 `/api/incoming-documents/extractions/query` 查询来文处理结果。
2. 后端返回摘要、分类、结构化结果和来文处理状态。
3. 运行聊天时，后端把摘要注入 iframe runtime context。
4. 当摘要不足以回答细节问题时，后端把该来文的 markdown 临时写入当前 thread sandbox，并在 prompt 中给出 `read_file` 路径。

这个方案复用现有 `iframe_context_service.py` 的长页面落盘模式和现有 `read_file` 工具边界。`read_file` 不直接读 MinIO 或数据库。

### 4.4 入知识库语义

“存入知识库”不是外部系统上传后自动入库，而是：

1. 外部系统上传来文，只进入“来文管理”。
2. 管理员打开来文详情，选择目标知识库和入库参数。
3. 管理员点击“存入知识库”。
4. 系统自动创建知识库文件记录，并完成解析、切片、embedding、索引。

因此它是“人工触发入库，系统自动完成后续流程”。

### 4.5 入库设置复用

来文管理不复用整个 `FileUploadModal`，因为来文已经上传过了，不需要上传区域、URL 输入、工作区文件选择。

来文管理需要复用：

- `ChunkParamsConfig`：入库参数配置。
- 知识库文件夹选择逻辑。
- OCR 引擎选择逻辑。
- `buildChunkParamsPayload`：参数构建规则。
- 现有知识库 API 的参数结构：`auto_index=true`、`chunk_preset_id`、`chunk_parser_config`、`ocr_engine`、`ocr_engine_config`。

来文专用“存入知识库”弹窗/抽屉只保留目标知识库、存储位置、OCR、入库参数和确认按钮。

### 6.2 状态定义

`incoming_documents.status`：

- `uploaded`：原文件已保存，等待处理。
- `parsing`：正在解析 markdown。
- `summarizing`：正在分类、摘要、结构化抽取。
- `ready`：摘要和解析结果可用。
- `failed`：来文处理失败。

`knowledge_import_status`：

- `none`：未入知识库。
- `importing`：已提交入库任务。
- `indexed`：知识库入库完成。
- `failed`：知识库入库失败。

### 6.3 来文上传流程

`POST /api/incoming-documents/ingest`

输入支持两种方式：

1. `multipart/form-data`：外部系统直接上传文件。
2. JSON：传入 `sourceUrl/sourceKey/filename/sourceSystem/sourceDocumentId`，后端下载文件。

处理流程：

1. 校验登录用户，v1 继续使用当前认证体系，不新增外部 API Key。
2. 计算幂等键 `(source_system, source_document_id)`。
3. 如果 `source_document_id` 为空，则用 `source_key` 作为幂等 ID。
4. 如果已有记录且 `content_hash` 相同，直接返回已有 `incoming_id`。
5. 如果已有记录但 `content_hash` 不同，覆盖当前记录、清空旧摘要和入库关联字段、重新处理。
6. 文件写入 MinIO incoming 前缀，例如 `incoming/{source_system}/{incoming_id}/{filename}`。
7. 创建或更新 `incoming_documents`。
8. 提交后台任务：解析 markdown、分类、摘要、结构化抽取。

删除现有逻辑：

- 删除 `INCOMING_DEFAULT_KB_ID` 配置依赖。
- 删除来文上传阶段默认创建 `KnowledgeFile` 的行为。
- 删除上传后自动提交知识库 business extraction 的行为。

### 6.4 来文处理任务

任务类型固定为：`incoming_document_process`

任务步骤：

1. 从 MinIO 读取原文件。
2. 调用现有 `Parser.aparse()` 生成 markdown。
3. markdown 写入 MinIO incoming parsed 前缀。
4. 根据 markdown 做主分类。
5. 生成完整摘要。
6. 生成结构化抽取结果。
7. 更新 `incoming_documents` 和 `incoming_document_extraction_runs`。

长文档处理：

- markdown 字符数不超过 12000 时，直接一次分类摘要。
- 超过 12000 时，分段摘要后再合并。
- 合并结果必须包含全文摘要，不只包含结构化字段。

### 6.5 查询接口

`POST /api/incoming-documents/extractions/query`

输入：

```json
{
  "files": [
    {
      "id": "att-001",
      "name": "client-review.pdf",
      "sourceKey": "business-file-001",
      "sourceUrl": "https://business.example.com/files/001"
    }
  ],
  "sourceSystem": "oa",
  "sourceDocumentId": "doc-001"
}
```

输出按文件返回：

```json
{
  "items": [
    {
      "incomingFileId": "att-001",
      "incomingId": "inc_xxx",
      "matchStatus": "matched",
      "processingStatus": "ready",
      "classification": "客户审查",
      "summary": "该附件主要说明...",
      "structuredResult": {},
      "hasMarkdown": true,
      "knowledgeImportStatus": "none",
      "linkedKbId": null,
      "linkedFileId": null
    }
  ]
}
```

状态语义：

- `matched`：找到来文记录。
- `pending_sync`：未找到记录，但前端提供了 `sourceUrl/sourceKey`，可以调用 ingest。
- `not_found`：未找到记录，也没有足够信息同步。
- `multiple`：匹配到多个候选，v1 不自动选择。

### 6.6 chat-iframe 上下文注入

`render_iframe_context_prompt()` 增加来文处理：

1. 对 ready 来文，注入分类、摘要、结构化结果摘要。
2. 对 `hasMarkdown=true` 的来文，在当前 thread sandbox 下写入 markdown 文件。
3. prompt 中暴露 `read_file` 路径，例如 `/home/gem/user-data/uploads/iframe-context/incoming/inc_xxx.md`。
4. 对未处理完成的来文，明确提示“正在处理，不能猜测附件内容”。

上下文限制：

- 单个来文摘要注入上限 1200 字。
- 多来文总注入上限 8000 字。
- 完整 markdown 不直接塞入 prompt，只通过 `read_file`。

### 6.7 存入知识库接口

新增：

`POST /api/incoming-documents/{incoming_id}/knowledge-import`

请求体：

```json
{
  "kb_id": "kb_xxx",
  "parent_id": null,
  "params": {
    "content_type": "file",
    "auto_index": true,
    "ocr_engine": "mineru",
    "ocr_engine_config": {},
    "chunk_preset_id": "general",
    "chunk_parser_config": {}
  }
}
```

处理流程：

1. 校验当前用户为管理员。
2. 校验来文存在且 `original_file_url` 可用。
3. 校验目标知识库支持文档入库。
4. 如果 `knowledge_import_status=importing`，返回 409。
5. 如果已有关联 `linked_kb_id/linked_file_id` 且状态为 `indexed`，返回已有结果。
6. 构造 items：`[original_file_url]`。
7. 构造 params：
   - `content_type=file`
   - `auto_index=true`
   - `parent_id`
   - `content_hashes`
   - `file_sizes`
   - OCR 参数
   - chunk 参数
   - `source_paths` 映射，key 为 `original_file_url`，value 为 `来文/{classification}/{filename}` 或前端选择的目录路径。
8. 调用抽出的共享知识库 ingest service。
9. 立即保存 `knowledge_import_task_id` 和 `knowledge_import_status=importing`。
10. 任务添加知识库文件记录后回写 `linked_kb_id/linked_file_id`。
11. 任务索引成功后回写 `knowledge_import_status=indexed`；失败时回写 `knowledge_import_status=failed` 和错误原因。

关键约束：

- 后端不直接硬编码默认 chunk/OCR 参数。
- 后端不复制 `knowledge_router.py` 中的解析、入库循环。
- 应把 `add_documents()` 内部“添加记录 -> 解析 -> auto_index 入库”抽为 service，例如 `KnowledgeDocumentIngestService`。
- `knowledge_router.py` 和 `incoming_document_router.py` 都调用该 service。

入口：详情抽屉和列表操作列。

界面字段：

- 目标知识库：下拉选择管理员可访问且支持文档入库的知识库。
- 存储位置：目标知识库文件夹 TreeSelect，默认根目录。
- OCR 引擎：复用现有 OCR 选择逻辑。
- 入库参数：复用 `ChunkParamsConfig`。
- 确认按钮：`存入知识库`。

不展示：

- 文件上传拖拽区。
- URL 输入。
- 工作区选择。
- “上传后自动入库”开关。

因为这个入口本身就是入库动作，提交时固定 `auto_index=true`。

### 7.5 API 封装

新增 `web/src/apis/incoming_documents.js`：

- `listIncomingDocuments(params)`
- `getIncomingDocument(incomingId)`
- `retryIncomingDocument(incomingId)`
- `importIncomingDocumentToKnowledge(incomingId, payload)`

chat-iframe 侧保留自己的 `chat-iframe/src/apis/incoming-documents.ts`，但返回字段要与后端新结构对齐。

## 8. 知识库流程复用设计

当前 `knowledge_router.py` 的 `add_documents()` 同时承担 API 参数处理、任务提交和具体 ingest 编排。实现本方案时需要做一次小范围下沉：

新增服务：

`backend/package/yuxi/services/knowledge_document_ingest_service.py`

职责：

1. 接收 `kb_id/items/params/operator_id`。
2. 添加知识库文件记录。
3. 解析文件。
4. 根据 `auto_index` 决定是否入库。
5. 返回任务结果和每个文件的 `file_id/status`。

调用方：

- 知识库上传接口继续调用该 service。
- 来文“存入知识库”接口也调用该 service。

这样可以复用现有知识库入库行为，同时减少 `knowledge_router.py` 继续变胖。

## 9. 权限与安全

1. “来文管理”页面仅管理员可见。
2. 来文列表、详情、重试、存入知识库接口使用 `get_admin_user`。
3. 外部系统上传接口 v1 继续使用当前登录认证体系，不新增匿名上传。
4. chat-iframe 普通用户只能通过查询接口获得当前上下文匹配到的来文摘要，不提供全局来文列表。
5. `read_file` 只能读取当前 thread sandbox 中临时写入的 markdown，不暴露 MinIO 路径。
6. 存入知识库时使用管理员身份写入 `created_by/updated_by`，便于审计。

## 10. 错误处理与幂等

### 10.1 上传幂等

- 同 `(source_system, source_document_id)` 且 hash 相同：返回已有记录。
- 同 `(source_system, source_document_id)` 但 hash 不同：覆盖当前来文处理结果并重新处理。
- 不做版本历史。

### 10.2 来文处理失败

- `status=failed`
- 写入 `processing_error`
- 列表展示失败原因。
- 管理员可点击“重试处理”。

### 10.3 知识库入库失败

- `knowledge_import_status=failed`
- 保留来文本身摘要和 markdown。
- 展示失败原因。
- 管理员可以重新打开入库弹窗调整参数后再提交。

### 10.4 已入库重复点击

- 入库中返回 409。
- 已入库返回已有 `linked_kb_id/linked_file_id`，不重复创建知识库文件。

## 13. 验收标准

1. 不配置 `INCOMING_DEFAULT_KB_ID`，外部系统仍可上传来文并生成摘要。
2. 上传来文后，知识库列表中不会自动出现该文件。
3. chat-iframe 可以拿到来文摘要；摘要不足时，模型能通过 `read_file` 读取完整 markdown。
4. 管理员可在 Web“来文管理”中查看来文列表、详情、摘要、分类和处理状态。
5. 管理员点击“存入知识库”前可以选择知识库、目录、OCR 和入库参数。
6. 点击“存入知识库”后，系统自动解析、切片、embedding、索引。
7. 入库成功后，来文记录展示目标知识库和知识库文件 ID。
8. 来文入库后的文件在目标知识库中可检索、可问答。
9. 失败状态可见，管理员可以重试来文处理或重新提交知识库入库。

5. 自动清理、归档、物理删除。
