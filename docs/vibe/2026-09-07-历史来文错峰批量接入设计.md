# 历史来文错峰批量接入设计

> 2026-09-07 深度审核修订：已对照本分支源码、Compose 和 ARQ 0.28.0 源码核实。本文是待实施的设计约束，不代表功能已经实现或生产性能已经验证。第 16 节记录证据和审核结论。

## 1. 背景

系统存在三类来文接入入口：

1. 用户使用小助手时发现来文尚未解析，需要立即上传并解析。
2. 当前上级新发来的来文，需要立即上传并解析。
3. 历史来文批量补录，初期约 2000 份，后续可能扩展到几万份。

前两类属于高优先级即时任务，历史来文属于低优先级任务。历史任务只能在每天 18:00 至次日 07:30 启动，07:30 后不再启动新的历史任务；已经运行的历史任务允许自然完成，即使偶尔超过 08:00 几分钟。

历史来文由上游系统提供长期有效的来文 ID 和下载接口，因此批量登记时只需要保存下载元数据，不需要在工作时间集中下载文件。

## 2. 目标

- 支持一次登记约 2000 份、后续扩展到几万份历史来文。
- 即时任务全天优先处理，历史任务仅在规定时间窗口内补充空闲处理能力。
- API 或 Worker 重启后任务不丢失、可恢复、可重试。
- 避免历史任务大量堆积在 Redis，PostgreSQL 作为任务状态的唯一事实来源。
- 原始文件、附件和解析产物由 MinIO 保存，PostgreSQL 不保存大文件二进制。
- 支持只重新执行分类和结构化抽取，不重复下载和解析文件。
- 提供运维必需的精简管理页面，能够查看进度、失败原因并执行有限的人工操作。

## 3. 非目标

- 首版不提供手工拖动任务排序。
- 首版不直接展示或编辑 Redis 内部队列。
- 首版不建设复杂报表、容量预测或多级审批流程。
- 测试环境暂不启用 MinerU OCR，也不修改现有解析参数。
- 首版不为百万级以上任务提前设计分库分表。
- 首版不支持来文 Worker 多副本部署，不建设通用分布式资源调度框架。
- 历史接入完成不自动确认来文、不自动启用通知任务、不自动导入知识库。

## 4. 总体架构

PostgreSQL、Redis 和 MinIO 分工如下：

| 组件 | 职责 | 不承担的职责 |
| --- | --- | --- |
| PostgreSQL | 批次、任务元数据、状态、优先级、阶段、重试次数、错误、分类和结构化结果、MinIO 对象地址 | 不保存 PDF、Word、图片等大文件二进制 |
| Redis/ARQ | 保存少量已经获得执行资格的 `job_id` | 不保存完整历史积压，不作为任务状态事实来源 |
| MinIO | 保存原始来文、附件、Markdown、解析图片等对象 | 不负责业务状态、优先级和任务调度 |

建议新增独立的来文队列和来文 Worker，与 Agent/小助手 Worker 隔离。隔离队列可以防止历史任务占满小助手队列，但不会自动解决 MinerU、本地模型、GPU 等下游资源竞争，因此来文 Worker 初始并发设为 1，经过压测后再决定是否提高到 2。

具体采用一个 `incoming-worker` 和一个轻量 `incoming-dispatcher`，复用现有后端镜像、数据库连接方式及 ARQ 依赖。来文下载解析不放进现有通知/Agent 的 `scheduled_jobs` 表或 dispatcher 动作中；可以参考其短事务认领模式，不复用其业务状态机。

并发 `C` 是整份来文的在途数量，不能替代下游调用限制。目前 `process_incoming_document`、附件摘要和长附件摘要归并均存在 `gather` 扇出。首版将来文内的下载、附件解析、附件摘要及分块摘要调用串行执行，业务抽取沿用现有串行分块实现，保证 `C=1` 时来文链路不会同时发送多个解析/模型请求。全部三个入口、重试及分类纠偏必须经过同一执行准入。其他知识库和聊天任务仍共享下游服务，不能声称全系统并发被限制为 1。

## 5. 数据设计

### 5.1 批次

新增 `incoming_ingest_batches`，不要使用已有 `incoming_task_batches`，后者属于抽取后的通知任务候选领域。

- 保存批次名称、来源系统、创建者、客户端 `batch_key`、登记完成标记、暂停标记和时间戳。
- 批次生命周期为 `registering / active / paused / completed / completed_with_errors`；有终态失败时不能显示全成功。
- 新增 `incoming_ingest_batch_items`，以 `(batch_id, source_system, source_document_id)` 唯一关联接入任务。跨批次重复登记共享同一个来文任务，不复制下载和处理。
- 分别统计新登记、复用已完成、复用待处理、冲突项；相同身份但不同待处理输入不能静默覆盖。成员记录保存提交结果和目标输入版本，非法/冲突项可以没有 job_id；批次不能因忽略这些项而显示全成功。
- 进度用已登记成员关联任务的数据库分组查询计算，初期不保存多份可漂移计数。任务结束时记录对应成员的终态及版本，已结束批次保存完成时的摘要；以后独立重分析不倒改已完成批次的历史结果。页面区分批次成员完成结果与当前作业状态。
- 同一历史任务属于多个批次时，只要有一个已提交且未暂停的批次允许执行即可；暂停某批次不暂停其他批次或即时任务。页面展示这一复用关系。

### 5.2 任务

新增 `incoming_ingest_jobs`，每份来文一条可复用的任务主记录：

- 唯一身份沿用 `(source_system, source_document_id)`，外部仍使用 `document_metadata.source_doc_id`；附件身份沿用 `source_file_id`，不得改用文件名或下载 URL。
- 保存结构化的待下载清单、名称、公共元数据、来源入口、即时/历史优先级、创建者与最近操作者。
- 调度状态 `pending / dispatching / queued / running / succeeded / failed / cancelled` 和处理 `stage` 分开保存；另存 `next_attempt_at`、执行次数、最后错误、`delivery_token`、`lease_owner`、`lease_expires_at`、心跳及时间戳。
- 保存输入版本/指纹、操作类型 `resume / reanalyze / reparse / refresh_source`、解析参数快照、规则版本、当前抽取运行 ID。`delivery_token` 每次重新准入生成，不把重新投递误当成新业务版本。
- 增加 `input_ready` 区分同步上传尚在接收和可执行任务；接收中的状态为 `pending`、阶段为 `receiving`、`input_ready=false`，由独立接收租约保护，调度查询必须排除它。
- 原件和 Markdown 的有效地址仍由现有 `incoming_document_files` 保存，分类/抽取结果仍由现有业务表保存；任务只保存编排引用和未下载清单，避免两套业务数据长期漂移。

登记历史任务时可以尚无 `incoming_documents` 业务记录，先仅创建任务和清单。现有附件表 `original_file_url` 不允许为空，必须等该附件上传 MinIO 后才创建附件记录，不写假 URL、不为排队修改该约束。`incoming_id` 沿用现有稳定算法，任务记录可在业务记录创建后补关联。

同身份的即时请求命中历史任务时走独立的提优先级操作：不重复下载、不改变已有完整附件清单。完整来源更新和“希望尽快处理”是不同操作，后者不能用 iframe 的部分附件信息覆盖已登记清单。执行中禁止替换输入，按现有接口返回冲突；已完成且内容未变时复用结果。只有长期 ID 而没有上游版本号/哈希时，无法只凭 ID 判断文件是否变更；显式重新提交内容/刷新来源后下载算哈希，保留现有内容更新能力。

索引至少覆盖身份唯一约束、待投递任务的 `(priority, next_attempt_at, created_at, id)`、在途状态的租约到期时间和批次成员关联。任务、批次外键及删除规则应同时建入数据库模型和现有 schema migration 路径。

### 5.3 保留策略

- 来文业务记录、附件关系、分类结果和结构化结果长期保留。
- 任务主记录首版不自动删除。几万到几十万条元数据对 PostgreSQL 压力较小，并且这些记录对审计、排错和重跑有价值。
- 重试更新同一任务，不为每次重试复制完整任务数据；任务主记录覆盖最新执行状态，既有结构化抽取运行仍按运行保留，不能承诺数据库只增长任务元数据。
- Redis 中的执行数据在任务完成后清理。
- 不把完整运行日志写入 PostgreSQL，仅保存最后错误和有限的尝试记录；如后续增加详细事件表，可保留 90 至 180 天。
- MinIO 中正式原件和可复用的 Markdown 长期保留；失败产生的未引用对象按专用前缀核对后清理。解析图片只要被有效 Markdown 引用就是正式产物，不能按“图片/临时文件”统一过期删除。
- 不默认启用对象历史版本的无限保留。数据库抽取运行、图片对象和来源文件变更也是容量增长项，不能用“重试更新主记录”代替整体容量观察。

## 6. 任务阶段与重跑

每个附件独立记录成功检查点；任务保存正在执行的阶段：

```text
registered -> downloading/uploading -> parsing -> analyzing -> building_candidates -> succeeded
```

阶段产物保存后支持三种操作：

- 重新分析：复用已有 Markdown，重跑分类、附件摘要、结构化抽取及候选构建；默认保留人工指定的分类作为抽取路由，显式选择重新分类才覆盖 AI 分类，不静默清空人工结论。
- 重新解析：从 MinIO 原始文件重新生成 Markdown，然后重新分析。
- 重新下载：仅在上游文件内容发生变化或原始对象丢失时执行。

这样客户调整分类规则或结构化字段时，不需要重新调用 MinerU 解析全部历史文件。

任一阶段都可能失败。所有附件必须有有效 Markdown，主文件分类、主文件结构化抽取、副附件摘要及现有任务候选构建均成功后，才发布整份来文 `ready`。沿用现有业务语义：副附件参与解析和摘要，不在本次调整为全附件结构化抽取。

- 下载一份附件后立即上传并记录检查点，释放二进制缓冲，再处理下一份，避免把整份来文的所有附件积存在内存中。原接口单文件 100 MB 限制继续有效；大批量接口只收元数据。
- 某附件失败不清空其他附件的成功 Markdown；恢复时按内容哈希及解析参数快照验证后复用。不要继续调用当前会清空所有 `markdown_file_url` 的 `retry_processing` 实现。
- 解析复用指纹只包含原件内容哈希、解析器/版本及影响文本的配置，不包含执行令牌、图片输出前缀或运行时间；否则每次重试都会失去复用资格。只改业务元数据/分类规则时重新分析，文件内容和解析配置未变时不重复解析。
- 只在上传成功后提交对象地址；数据库提交失败产生的未引用对象不会被当作成功检查点。
- 原件、Markdown 及图片按内容/解析版本和执行令牌使用独立对象前缀，避免失去租约的旧执行者覆盖固定 `original.pdf` / `parsed.md` 路径。有效引用在短事务内切换；被知识库、审计或有效 Markdown 引用的旧对象不得随意清理。
- `incoming_document_markdown_service.py` 当前按固定文件路径缓存对话中的 Markdown 和原件。支持重新解析/更新来源后，落盘缓存键必须包含有效产物版本/哈希，避免旧对话永久读取旧文件。

现有 `IncomingTaskCandidateService` 会拒绝重建已冻结的候选批次，现有知识库入库状态也会阻止替换和纠偏。这些约束继续保留，登记重处理时提前检查，并在最终发布事务内再次检查。自动处理仅生成待确认候选，不确认来文、不触发历史通知。候选构建失败时复用本次已经成功的抽取运行，避免再次调用模型。

在来文记录上增加可空的 `published_extraction_run_id`，新流程完成时与候选、`ready` 和任务成功状态在同一事务内发布。来文查询/预览读取该运行，避免当前“取最新 success 运行”的逻辑暴露旧 Worker 的过期产物；旧数据回填最近成功结果，已有候选批次则优先使用其绑定运行。找不到有效运行时保留可诊断状态，不伪造完成。

现有仓储多使用各自的会话；涉及执行令牌验证、有效附件地址和最终结果发布的写入，需要使用调用方传入的同一个 session。所有提交检查 `delivery_token + 输入版本 + 当前租约`，旧执行者更新行数为 0 时立即退出，不发布结果、不重建候选。重处理过程中现有已发布结果保留在数据库，但对外仍按处理状态展示，不能把处理中/失败误报为新结果已完成。

## 7. 投递与执行规则

### 7.1 准入与优先级

时区固定 `Asia/Shanghai`，窗口是本地时间 `time >= 18:00 OR time < 07:30`，07:30 整不含在内。时间来自数据库并显式转换时区，不能依赖容器默认 UTC；持久化时间沿用项目 UTC 约定。

设并发为 `C`，首版单实例、`C=1`。有效在途数为 `dispatching + queued + running`，包括未确认投递的槽位；只投递空闲容量，不再使用原稿含混的 `C～2C` 预填队列。正常状态下在途数最多 `C`，历史积压始终在 PostgreSQL。

1. 即时任务提交事务后立即调用一次公共投递函数；投递失败不撤销已经登记的任务。历史批次完成登记后也调用同一函数。
2. 投递、Worker 开始执行、提优先级、批次暂停和恢复操作，用同一个事务级 advisory lock 串行化短暂准入决策；再按固定顺序锁任务/批次记录。锁内只执行数据库操作，禁止持锁下载、调用 Redis、解析或调用模型。单纯 `COUNT` 后再 `SKIP LOCKED` 无法防止两个投递者同时抢到最后一个容量。
3. 在短事务中选择已经到 `next_attempt_at` 的即时任务优先，然后才选择窗口内且批次可运行的历史任务；同优先级按创建时间、ID 稳定排序。写 `dispatching`、新令牌和投递租约后提交。
4. 事务外向独立 ARQ queue 投递 `process_incoming_document_job(job_id, delivery_token)`，`_job_id = incoming:{job_id}:{delivery_token}`。确认成功后仅对相同令牌、仍为 `dispatching` 的行改成 `queued`，不能把已经 `running/succeeded` 的状态改回去。
5. Worker 接到消息后重新读取数据库，在准入锁内验证令牌和状态；允许从 `dispatching` 或 `queued` 原子转入 `running`，兼容“Redis 已收消息但数据库尚未标记 queued”。若历史窗口已关闭、批次已暂停或已有到期即时任务等待，则该历史消息不运行，释放预约并返回待处理，由统一投递补位；不消耗执行重试次数。
6. 优先级以开始执行事务为界，已经开始的历史任务不抢占。夜间出现即时任务可能等待当前历史来文自然结束；这里的“即时”指无需等待夜间窗口，不承诺零排队或响应时限。若实测等待过长，再评估按附件/阶段让出执行权，首版不增加抢占框架。
7. 完成/失败释放槽位后立即尝试补投；独立 dispatcher 每 5 秒对账补投，保证 API/Worker 补投中断也不会丢任务。无历史任务时也是低频索引查询，不调用解析或模型；首版不再增加 30～60 秒空闲轮询模式，避免即时投递失败后等待过久。

暂停批次和 07:30 截止都必须在 Worker 真正开始时再次检查，不能只控制生产者。运行中的整份来文自然完成，后续附件属于该在途任务；不会因为跨过截止时间被强制终止。超大或附件多的来文可能远超过 08:00 几分钟，这不是时间门禁能保证的指标。样本压测发现长尾任务时，可提前停止新历史任务或对这些任务单独安排早夜间执行；不得声称 30 分钟缓冲能给出硬时限。

### 7.2 故障恢复与重试

- 投递超时不代表 Redis 未收到消息。保持 `dispatching` 和同一令牌，由 dispatcher 在投递租约内用相同 `_job_id` 重试；ARQ 返回 `None` 表示 ID 已存在，不是业务失败。
- 定期扫描到期投递租约和运行租约。Redis 消息丢失/过期、进程重启、任务死亡都以 PostgreSQL 对账；仅确认租约过期且不可继续的预约才失效令牌、回到 `pending`，下一次准入使用新令牌。旧 Redis 消息无论晚到或重复都不能通过数据库检查。
- 运行中每 15 秒续约，租约初值 120 秒；投递租约初值 60 秒。心跳使用独立短事务，耗时同步解析继续在线程/独立工作进程执行，不能阻塞心跳事件循环。续约失败时停止发起下一次外部调用和发布结果。
- 交付语义为“至少一次消息、幂等业务发布”，不承诺外部下载、OCR 或 LLM 调用绝对只发生一次。网络分区或进程故障时，旧外部请求可能仍在服务端执行；执行令牌只能阻止其覆盖有效业务结果，不能撤销已发出的 GPU 工作。
- 业务重试由 PostgreSQL 唯一管理。独立 ARQ 设置显式 `max_jobs=C`、`max_tries=1`、`retry_jobs=False`、`keep_result=0`，任务异常由包装层落库，异常退出由租约回收；不要继承 Agent Worker 配置。消息 `_expires` 显式设为 1 小时，超过投递租约就由数据库恢复，不靠 Redis 保存多夜积压。
- 可恢复错误（连接失败、429、5xx 等）初始最多执行 3 次，退避 1 分钟、5 分钟并记录 `next_attempt_at`。无效文件、404/权限错误、格式不支持、OCR 未启用和确定性校验失败进入终态失败，等待修正后人工重试。底层目前把下载错误包装为 `ValueError`，实施时需保留机器可判别的错误码，不能靠错误文本匹配。
- 历史重试、重分析、重新解析均遵守夜间窗口；管理员点“重试”保留原优先级，点“立即处理”才提优先级。只有全部成员进入终态后批次才完成/部分失败；等待夜间、暂停或退避不属于完成。人工重试重置本轮尝试计数并保留累计次数；批次重试只选择该批次失败成员，重新打开对应批次，失败项不会无休止占槽位。
- 设置明确的单任务总时限，初期沿用当前 Tasker 的 21600 秒上限并按压测收紧，不能误用 ARQ 默认 300 秒；下载、单次模型调用和 MinerU 请求各自保留超时。总时限不等于能杀死 `asyncio.to_thread` 内部调用：本地调用未退场时该 Worker 不接新来文，优雅退出后由进程管理器恢复；外部服务仍需自身并发/超时配置。`stop_grace_period` 与部署停机说明同步配置。
- 一次已超时且下游状态不明的解析尝试进入明确失败状态，不立即自动重复调用；先确认下游恢复后人工重试，避免不断增加未结束的解析请求。

### 7.3 批量登记与现有入口

新增管理员批次 API：`POST /api/incoming-documents/ingest-batches` 创建批次，`POST /ingest-batches/{id}/items` 分块登记，`POST /ingest-batches/{id}/submit` 完成登记后才允许历史处理；后两项路径同样位于 `/api/incoming-documents` 下。配套 GET 列表/详情、pause/resume、批次失败项重试接口。批次 API 以 `get_admin_user` 校验权限，服务端 API Key 复用已有管理员用户关联方式。

批次区分首次接入和重新分析/解析操作。已完成来文的批量重处理创建新的执行批次，成员绑定新输入/操作版本，使用同一分块登记和提交机制，保证低优先级重处理有可暂停的有效批次，不因原批次已完成而永远无法调度。普通失败恢复可以重新打开原批次。成员绑定的旧操作版本已经终结后，不再为新操作提供执行资格。

单次分块建议最多 200 条来文且请求体不超过 5 MiB，每份携带现有 `document_metadata` 与完整 `files` 元数据。每块先校验，合法项独立登记，返回逐项 `accepted / exists / conflict / invalid` 结果；客户端记录失败项并可以重复提交。`batch_key` 和成员唯一约束保证网络重试幂等。一个来源清单可以含 2000/几万项，由接入脚本自动分块、续传和最后提交，用户只需发起一次导入，不要求单个 HTTP 请求包含全部任务。未提交批次不运行，部分登记可在管理页看见。

首版维持现有 `/ingest` 请求字段、JSON 下载接收和 multipart 收文件的约定：成功 `accepted` 仍表示文件已经接收并交给后台处理；将后台执行从 Tasker 替换为持久任务。历史元数据受理使用独立批次接口，不能悄悄改变老接口中下载错误的同步响应语义。新到来文和 multipart 的同步接收必须先原子登记输入版本和接收租约，标记接收中、尚不可调度；接收完成后才置为可调度，接收失败可诊断和重试，不允许两个请求同时重置业务状态。接收租约期间不持数据库事务，客户端流无法在进程重启后恢复时要求重新上传。

`/extractions/query` 无论是否已经匹配到上传附件，都按来源身份关联当前接入任务，并返回任务 ID、优先级和处理状态，覆盖“部分附件已上传但任务仍在历史队列”的情况。iframe 发现未完成的历史任务时调用 `POST /api/incoming-documents/ingest-jobs/{job_id}/expedite`，不重新下载；该接口沿用即时接入的鉴权边界并验证提交的来源身份，仅允许提优先级。普通轮询查询不自行提优先级，避免运维浏览触发处理。没有任务时沿用现有自动补传，有任务时继续轮询状态直到业务 `ready`；终态失败明确显示，不自动无限重试。提优先级只更新当前优先级，不自动重开终态失败或已删除任务。

新增任务详情 API 供状态查询，保留 ingest 响应的 `taskId` 字段但明确它现在指向接入任务；同步检查任务中心/脚本中对旧 `/tasks/{id}` 的依赖。纠偏入口提交 `reanalyze` 作业并返回 `accepted + taskId`，现有 Web “已重新抽取”的同步提示改为“已提交”，随后查询真实完成状态。

## 8. MinIO 容量与运行要求

几万份来文本身不会对 MinIO 构成明显的对象数量压力，核心约束是总字节数、磁盘余量、部署可靠性和备份策略，而不是“几万个对象”。

本仓库 Compose 实际是单节点、单数据目录 MinIO：`./docker/volumes/milvus/minio`，Milvus 也连接同一实例。容量规划必须计入现有对象、Milvus、知识库增长及宿主机共用磁盘；仅凭 Compose 不能确认生产磁盘类型、剩余空间或 IOPS。扫描件的一份来文可能生成数百张图片，对象数应按实际产物估算。

容量应按下式估算：

```text
新增有效数据 = 来文数 x 平均原件及附件大小 x 解析产物系数
所需磁盘容量 >= (已有占用 + 新增有效数据 x 存储冗余系数 + 其他预计增长) / 目标使用率
```

- 解析产物系数包含原件、Markdown 和图片总和与原件大小之比；1.2 至 2.0 仅作演算假设，不是扫描件的上界。上线前以实际产物测量。
- 当前单目录部署没有 MinIO 多盘冗余；分布式或纠删码部署按实际数据盘/校验盘计算冗余，不笼统等同于副本数。备份容量另外计入备份系统。
- 建议长期磁盘使用率控制在 70% 至 80% 以下，并在 70%、80%、90% 设置分级告警。

示例（十进制 MB/GB，不含已有数据和备份）：2 万份来文平均原件和附件合计 10 MB，产物系数 1.5，新增有效数据约 300 GB；目标使用率 70% 时应预留约 429 GB 磁盘。平均 30 MB 则约 1.286 TB。原稿的乘 1.3 是“在数据量上加 30%”，并不等于磁盘保留 30% 空闲，故修正。初期 2000 份按相同假设约为上述容量的十分之一。

上线运行还应具备：

- MinIO 数据卷使用持久化磁盘，而非容器临时文件系统。
- 监控可用容量、请求错误率和对象写入失败。
- 明确正式原件的备份或容灾策略。MinIO 持久卷不等同于备份。
- 对临时解析对象配置生命周期规则，不能误删原件和仍被业务记录引用的 Markdown。
- 对对象键使用稳定前缀，例如按业务类型、年份或来文 ID 组织；业务查询依赖 PostgreSQL，不通过全桶扫描查找来文。
- 批量写入的磁盘吞吐、IOPS、网络、临时解析目录空间和 PostgreSQL/WAL 所在磁盘也要观察。空间足够不代表磁盘延迟不会影响 Milvus 和小助手。
- 现有解析图片写入公开可读 `public` 桶，这是当前权限边界，不因 PostgreSQL 任务鉴权而变成私有。生产必须核对该部署的网络/网关访问边界；如来文要求逐用户保密，需先完成鉴权图片访问设计，不能仅用不可猜测的对象名声称隔离。

## 9. OCR 上线配置

测试环境暂不修改 OCR 参数。已核实 `_resolve_ocr_engine_params` 默认为 `disable`；来文服务目前只传图片存储参数，没有独立来文 OCR 配置入口。设置 `MINERU_API_URI` 或修改知识库入库弹窗的 OCR 选项，都不会自动启用前置来文解析。

本次实施新增来文专用配置并传入 `Parser.aparse`，保持测试默认：

| 配置项 | 测试默认 | 线上 MinerU 启用后 |
| --- | --- | --- |
| `INCOMING_OCR_ENGINE`（新增） | `disable` | `mineru_ocr` |
| `INCOMING_OCR_ENGINE_CONFIG_JSON`（新增） | `{}` | `{"backend":"hybrid-engine","parse_method":"auto"}` |
| `MINERU_API_URI`（已有） | 维持现状 | DocMind Worker 可访问的 MinerU API 根地址 |
| `MINERU_BACKEND`（已有） | 维持现状 | 与线上 MinerU 版本实际支持的 backend 对应，当前 Compose 默认 `hybrid-engine` |
| `MINERU_TIMEOUT`（已有读取） | 1800 秒 | 按服务响应上限调整，需传入来文 Worker |

Worker 使用如下参数形状，并保存到任务解析快照；上述新增环境变量在实施后才生效，不能误认为当前已经支持：

```json
{
  "ocr_engine": "mineru_ocr",
  "ocr_engine_config": {"backend": "hybrid-engine", "parse_method": "auto"}
}
```

`INCOMING_OCR_ENGINE_CONFIG_JSON` 必须是 JSON 对象。其字段会覆盖 MinerU 的默认请求字段，未知字段也会透传给 `/file_parse`，以支持后续 MinerU API 增加参数而无需改动 DocMind；例如 `effort`、`table_enable`、`formula_enable`、`image_analysis`。但 `return_md`、`response_format_zip` 以及 `return_image`/`return_images` 继续由当前客户端固定，不能通过 JSON 改写，因为响应处理无条件按包含 Markdown 和图片的 ZIP 解包。`ocr_engine`、`ocr_engine_config`、`image_bucket`、`image_prefix`、`server_url` 等内部路由和存储字段也不得透传。

操作顺序：部署 MinerU 并从 Worker 网络验证健康/解析接口；修改线上 `.env` 中上表值并确认 Compose 透传；重新创建 `incoming-worker` 和 `incoming-dispatcher` 使环境变量生效；用电子 PDF、纯扫描 PDF、混合 PDF 和图片各跑样本；通过后提交历史批次。未启动任务在首次执行时固定参数快照，同一次失败恢复沿用该快照。切换 OCR 后对旧的扫描失败任务显式执行 `reparse`，创建新解析版本并重新取配置，普通 `resume` 不偷偷改变参数。

模型规格和分类/抽取规则版本同样进入快照，并作为显式参数传到分类、摘要及抽取函数，不能只在任务表记录版本、运行时仍不断读取变化的 `config.default_model`。规则文件/代码升级导致旧快照不可执行时，任务明确提示版本不匹配，管理员选择新版本重新分析；不构建无限历史规则仓库。

`auto`/`ocr` 的具体行为依赖线上 MinerU 版本和 backend，尤其不能假定所有 VLM/hybrid backend 都按 pipeline 的方式使用 `parse_method`。默认使用 `auto`，强制 `ocr` 只在该 backend 支持且样本验证后使用。普通 Office 文件仍走项目现有转换流程，启用 MinerU 不表示其中每一张内嵌图片都会被 OCR。

测试环境无 OCR 时纯图片会明确失败，纯扫描 PDF 可能产出空文本而失败，混合 PDF 可能只读出文字层；不能把非空 Markdown 当成扫描内容完整的证明。测试阶段可验证这些失败状态与恢复行为，真实 OCR 质量和吞吐验收留在线上服务可用后执行。

## 10. 精简管理页面

首版纳入精简管理功能。项目已经有 `web/src/views/IncomingDocumentsView.vue` 及管理员路由，优先在来文管理下增加“接入任务”页签/子视图，复用已有表格、详情和 API 层，避免另建重复的来文详情页面。批次登记由脚本/API 完成，首版无需开发浏览器大文件导入器。

页面读取 PostgreSQL，不以 Redis 队列内容作为真实状态，包含：

- 批次列表及总数、待处理、处理中、成功、失败和进度。
- 任务列表及来文名称、来源、优先级、阶段、重试次数、最后错误和更新时间。
- 按批次、状态、优先级和名称筛选。
- 暂停或继续历史批次。
- 重试失败任务。
- 按当前批次重试失败项，管理员单条和批量重分析入口复用同一 API；批量重处理保持历史优先级。
- 将尚未运行的历史任务提升为即时任务。
- 展示当前历史处理窗口和处理并发。

运行中任务首版不提供强制取消，避免中断下载、MinIO 写入或解析调用时产生不完整状态。管理页不提供 Redis 队列编辑和手工排序。

列表分页默认 20、最多 100，只返回概要、错误摘要和文件数量，不带完整下载清单、附件正文或源站敏感 URL；名称搜索通过显式查询提交，正文不参与搜索。任务详情按需读取。页面可见且有进行中任务时每 5 秒刷新当前页，隐藏/卸载停止，批次完成后停止轮询。显示“等待夜间窗口 / 批次暂停 / 等待空闲 / 重试退避 / 接收中”等原因，避免把尚未运行的任务都标成解析中。

管理列表、批次操作和重处理 API 仅管理员可用，不能只靠 Vue 路由守卫。下载清单复用现有 HTTP(S)、文件类型和大小校验；上游长期接口必须无需浏览器 Cookie 即可从 Worker 访问，来源 ID 长期有效不等于登录凭证长期有效。服务器端下载来源及重定向应限制在部署明确允许的上游地址范围，不能只用字符串判断 http/https；日志不输出访问令牌。

已有来文删除/归档需要同步处理：在途任务禁止物理删除；待执行任务删除时先在同一事务失效令牌、标记 `cancelled` 并移除有效来源关联，保留批次最小结果摘要，旧消息不得重新创建来文。归档使未执行历史任务停止自动投递。现有已确认/已启用任务的审计删除保护继续生效，首版不新增后台自动清理正式记录的操作。

## 11. 性能验证与上线策略

先选取 50 至 100 份具有代表性的文件压测，包括普通 PDF、扫描 PDF、图片、表格、大文件和旧 Office 格式，记录：

- 单文件平均、P95 和最大处理时间。
- 下载、解析、分类、结构化抽取各阶段耗时。
- CPU、内存、GPU 显存、MinIO 空间增长。
- MinerU、本地模型的排队、超时和失败率。

夜间理论处理量按以下方式估算：

```text
每日处理量约等于 13.5 小时 x 3600 / 平均单件耗时 x 并发数 x 有效利用率
```

有效利用率可先按 70% 至 80% 估算。只有当下游服务资源仍有余量且 P95、失败率没有明显变差时，才把并发从 1 提高到 2。

统计单位必须是“整份来文完成下载、全部附件解析、分析和候选构建”，同时记录每份附件数和页数，不能用单个 PDF 解析耗时估算整份完成量。这个公式中的有效利用率只用于基于孤立样本耗时的规划；若使用整夜实测吞吐，不再重复扣一次利用率。

首版沿用支持格式白名单。当前 `.ppt` 不在统一解析器白名单中；ZIP 仅处理含 Markdown/图片的解析产物包，不是任意 Office/PDF 附件压缩包。登记时提示不支持的格式；ZIP 解压后大小和条目数应设上限并测试，不能把 100 MB 上传限制当成解压内存上限。真实老格式样本先验证，不能因指南列了 MIME 示例就承诺都支持。

测试环境未部署 MinerU，测试中使用可控制的解析/模型替身验证队列与恢复，不据此宣称生产吞吐。当前审核主机未识别到 `docker` 命令，本次仅完成源码和设计静态审核，未进行运行环境压测。

## 12. 风险与控制

- 三个入口重复处理：通过上游来文 ID 唯一约束及任务提升解决。
- PostgreSQL 与 Redis 状态不同步：保留投递中状态，用同一令牌对账；超时失效后再生成新令牌，不能凭 Redis 超时直接重置。
- Worker 重启导致任务悬挂：使用租约、心跳和超时回收。
- 本地模型或 MinerU 并发不足：独立队列，并发初始设为 1，压测后调整。
- 分类或抽取规则变化：保存阶段产物及版本，支持只重新分析。
- MinIO 空间不足：上线前容量测算、阈值告警、临时对象生命周期和备份策略。
- 08:00 后影响小助手：07:30 在 Worker 启动处限制新历史任务，在途不抢占；超长来文必须通过样本识别，不能保证固定几分钟内排空。
- 新旧流程双重消费：切换时停止旧来文接收、排空旧 Tasker 来文任务，再迁移并开启新入口。其他 Tasker 用例不一起迁移。
- 已冻结候选和知识库索引被重处理破坏：保留既有审计保护，登记和提交都检查。

## 13. 实施范围评估

整体属于中等偏上的后端改动，不需要重写现有系统。可靠恢复和现有业务兼容占主要工作量，队列表本身不是难点。建议分两阶段实施：

1. 任务/批次/成员模型及迁移、分块登记、专用队列和 Worker、时间准入与租约恢复、附件检查点及结果原子发布；同步接入即时 API、iframe 提优先级及分类纠偏。
2. 复用来文管理页增加任务视图和运维操作，补齐端到端故障测试、部署配置和文档。

原稿后端 8 至 12 人日、页面 3 至 5 人日属于粗估，遗漏了输入接收并发、iframe 协同、候选/结果发布及缓存失效等工作。现按后端与接口联调约 10 至 15 人日、复用页面约 2 至 3 人日、故障/回归测试及上线文档约 3 至 5 人日估算，共约 15 至 23 人日；这是范围估算，不是交付承诺，不含等待线上模型部署及大批次实际处理时间。

收益优先保留可靠排队、串行限流、夜间门禁、附件断点、复用 Markdown 和必要管理操作。可延后的项包括 Worker 多副本、抢占调度、复杂统计、导入向导和自动容量清理。不得为了减少工期删除幂等令牌、Worker 时间复查或已有业务审计约束。

切换顺序：新增兼容表/字段；短暂关闭来文写入口，等待旧来文 Tasker 停止执行；确认没有旧任务仍能回写后，完成结果指针回填，并对遗留 `uploaded/failed` 记录创建可恢复作业（已有产物继续复用）；最后启动新 dispatcher/Worker、开放写入口。API 启动时的旧 Tasker 恢复逻辑不得把新作业改成失败。新服务初始化仅加载来文需要的配置与数据库，不运行 Agent 恢复钩子。迁移脚本应可重复运行，Worker 启动前确认 schema 就绪。

回滚先暂停历史批次和新写入口、停止新执行者并确认无在途写入，再恢复兼容版本；保留新增数据表和原件，不自动降级删除。新对象路径可由已有下载方式读取；新增任务仍以 PostgreSQL 保留，不能转投旧 Tasker 形成双执行。正式实现同步更新 `ARCHITECTURE.md`、来文接入指南、Compose/环境变量示例、变更日志及前端 API 文件；本次审核仅修订本设计稿。

## 14. 验收标准

- 一次登记 2000 份历史来文时，API 不执行解析，不向 Redis 堆积全部任务。
- 历史任务仅在 18:00 至次日 07:30 启动，07:30 后在途任务可自然完成。
- 即时任务全天可进入执行队列，并优先于尚未开始的历史任务。
- API、调度器或 Worker 重启后，未完成任务可从 PostgreSQL 恢复。
- 同一上游来文经不同入口提交时不会重复创建有效作业；正常竞争只执行一次，故障恢复允许外部调用重做但不得重复发布或覆盖新结果。
- 解析成功后可只重跑分类和结构化抽取。
- 无历史任务时调度器不调用下载、解析和模型服务，对数据库只产生低频索引查询。
- 管理页能查看批次进度、筛选任务、查看错误、暂停/继续批次并重试失败任务。
- MinIO 容量经过代表性样本测算，生产环境具备容量告警和正式文件备份策略。

实施后必须在 Docker 中完成以下测试；本表是验收要求，不是本次审核已经通过的测试：

| 场景 | 必须验证的结果 |
| --- | --- |
| 2000/几万条清单，分块提交中断后重传 | 用户一次操作、可续传；任务/成员不重复；请求不下载文件；未 submit 的批次不运行 |
| 17:59:59、18:00、跨午夜、07:29:59、07:30 | 上海时区边界正确；Redis 中旧历史消息 07:30 后不启动；在途自然完成 |
| 暂停后仍有 queued 消息，任务又被即时入口请求 | 历史消息先检查暂停；显式提优先级后全天执行，不被历史批次暂停阻挡 |
| 两个投递者同时看到一个空槽，或任务尚在 dispatching | 有效在途不超过 C；不得漏算未确认投递；不会把 running 写回 queued |
| Redis 已入队但客户端超时；入队后进程退出；消息 TTL 到期/丢失 | 同令牌对账、超期回收；最终可恢复；旧消息退出，无永久卡住 |
| Worker 死亡、租约失效后旧 Worker 又返回 | 旧写入不能改变有效附件引用、业务状态、结果指针或候选；允许记录诊断信息 |
| 一份来文有多个大附件，第二个解析失败 | 解析/模型调用并发符合配置；不缓存全部原件；重试复用已成功附件 |
| 抽取成功但候选构建失败，或完成事务中断 | 重试复用指定抽取运行；ready、候选与 published 运行一致，不发布半成品 |
| 更换模型规则后 reanalyze、启用 OCR 后 reparse | 前者无下载/解析请求；后者只重建解析及下游阶段；失败 resume 使用原参数快照 |
| 已冻结候选、已入库来文尝试重处理或删除 | 保留原审计/索引保护，返回清晰冲突，不清空既有结果 |
| iframe 命中待下载历史任务，部分附件已经上传 | 识别同一作业并提优先级，不把尚未上传误判为全新来文，也不因 matched 而永远等到夜间 |
| 重解析后原对话再次读取原件/Markdown | 缓存版本更新，读取有效产物；失败/旧 Worker 的产物不被取作最新成功结果 |
| 历史来文处理完成 | 生成草稿和候选，但不自动确认、不发送历史通知、不导入知识库 |
| 未授权用户访问管理 API，页面隐藏/关闭 | 后端拒绝管理操作；页面停止轮询；列表不泄露完整下载清单或凭证 |
| 无任何历史任务或历史全部完成 | 长时间观测只出现轻量数据库/ARQ 空闲轮询，无下载、OCR、LLM 请求 |

后端用例放在 `backend/test`，覆盖单元、真实 PostgreSQL/Redis 的集成故障测试及现有前端/iframe 回归。性能验证需在有实际服务的部署上记录资源和端到端耗时，不能以替身测试替代。
