# 模型上下文管理重构实施方案

> **供实施智能体使用：** 执行本文档前必须使用 `superpowers:executing-plans`，按阶段测试和复核，不得跳过验收门槛。

**目标：** 用模型预算驱动的有界工作上下文替代百分比摘要策略，使不同模型窗口、最低输出预留和工具调用规模下的会话都能持续运行。

**架构：** PostgreSQL 和线程文件保存完整历史，LangGraph 只保存滚动摘要与近期完整交互段。所有模型调用按标准化后的窗口、输出预留、安全缓冲和最终请求内容计算预算；大型工具结果采用“无损持久化 + 有界引用”，源文件读取采用原地分页而非二次卸载。

**技术栈：** Python 3.12、LangChain/LangGraph、DeepAgents middleware、FastAPI、PostgreSQL、Vue、Docker Compose。

## 全局约束

- 不根据模型名称、参数规模或固定窗口值编写分支。
- 不新增上下文微服务、数据库表或文件读取工具；继续使用现有 `read_file` 按行分页契约。
- 固定工具结果阈值只能作为最大内联上限，不能作为上下文安全线。
- 原始内容必须先持久化，再从模型工作上下文或 checkpoint 中移除。
- `read_file`、`open_kb_document` 等源文件窗口不得再次复制到 `large_tool_results`。
- 实施遵循测试先行，并在 Docker 容器内完成测试、格式化和 Lint。

## 2. 背景与根因

当前实现把模型窗口的 70% 用作摘要触发线，又从剩余比例推导出 15% 的摘要后保留窗口。该策略不能证明下一次请求一定能够放入模型，因为最终请求还包含：

- system prompt 和运行时附件上下文；
- 当前启用工具的完整 JSON Schema；
- 当前用户输入；
- 滚动摘要本身；
- 工具调用参数和工具结果；
- 最低输出预留；
- Tokenizer、消息协议和供应商统计差异。

固定保留消息数也不能解决问题：一条消息或一个工具结果就可能超过整个可用输入预算。一次摘要后直接重试同样不可靠，因为摘要文本和保留尾部合并后仍可能超限。

此外，DeepAgents 的 `_summarization_event` 主要改变发送给模型的有效消息视图，不能单独保证 LangGraph checkpoint 中的原始消息长期有界。会话足够长时，即使模型输入已经压缩，checkpoint 仍可能持续膨胀。

因此本次不继续调整百分比，而是建立以下唯一安全边界：

```text
可用输入预算 = 模型完整上下文窗口 - 本次最低输出预留 - 安全缓冲
```

## 3. 目标、保证与边界

### 3.1 必须达到的目标

1. 所有模型调用在发出前均按最终 system、tools 和 messages 计算预算。
2. 压缩后重新计数；仍超预算则继续压缩，直到满足预算或确认没有可继续缩减的内容。
3. 上下文溢出不能被普通模型重试转换成助手错误正文。
4. 完整原始历史先持久化，再从 LangGraph 工作状态中裁剪。
5. 历史会话长度和历史工具调用次数不再决定下一次模型请求能否继续。
6. 单条超长用户输入、工具结果和多模态内容不能直接占满后续工作上下文。
7. 内部摘要内容不得流向客户端或持久化为用户可见助手回复。
8. 同一套逻辑适用于不同供应商、不同模型窗口、不同最低输出预留和不同 Token 计数能力。

### 3.2 能够提供的保证

- 对已被 API 接受且已成功持久化的内容，原始数据不因压缩而丢失；工具结果持久化失败属于明确工具错误，不声明本次结果已保存。
- 模型工作上下文和 LangGraph 活跃消息保持在明确预算内。
- 可压缩内容存在时，上下文溢出会触发重新组装，而不是终止会话。
- 摘要失败或主模型失败时，不提交错误 cutoff，不破坏下一次继续聊天的状态。
- 旧内容可通过现有文件系统工具按路径、偏移量或关键词重新读取。

### 3.3 无法通过上下文管理解决的情况

- 模型服务不可用、鉴权失败或持续返回非上下文类错误。
- 模型配置的完整窗口小于 system prompt、工具 Schema 和最小请求的固定开销。
- 上游网关或数据库拒绝接收请求，内容尚未进入系统存储。
- 有限窗口模型不可能在一次调用中同时看到无限原文；系统保证的是完整存储、有界工作集和按需恢复。

上述情况必须返回明确的服务或配置错误，不能伪装成摘要成功。

## 4. 复审后的设计优化

相较最初第三种方案，本次复审做出以下收敛：

1. **不新增上下文微服务。** 继续复用 `YuxiSummarizationMiddleware`、LangGraph state、PostgreSQL 消息记录和现有文件后端，只替换预算和压缩控制流。
2. **不新增数据库表。** 模型限制继续存放在现有模型 JSON 配置中；消息、工具调用和工具结果继续使用现有表。
3. **不把 1024 Token 当作所有模型的固定真理。** 安全缓冲支持模型级配置，并保留部署级默认值作为校准旋钮。
4. **不为模型名称写分支。** 所有差异通过标准化后的 model profile、调用参数和 Token counter 能力解析。
5. **保留 TokenUsage 的独立职责。** 不创建巨型中间件；摘要中间件负责预算和恢复，TokenUsage 负责最终候选的统计，ModelRetry 只负责瞬时故障。
6. **不增加通用历史检索框架或读取工具。** 复用 `/outputs/conversation_history`、`read_file`、`grep` 和现有分页读取能力。单行超长内容维持现有按行读取/截断行为，不在本次上下文治理中承诺行内续读。
7. **不立即改造 AgentRun 的输入存储结构。** 当前 `Message` 与 `AgentRun.input_payload` 的重复存储不是模型上下文溢出的根因；仅在压力测试证明其成为存储瓶颈时单独处理。
8. **不长期保留双策略。** 最终删除 70% 触发线、15% 保留比例和固定保留消息数，不设置旧策略兼容开关。当前代码没有独立的 5% 尾部重试逻辑；实施时只删除已有文档中把 5% 描述为实际机制的错误表述，不能为“清理 5%”新增不存在的代码。
9. **区分普通大结果和源文件窗口。** 普通工具结果没有稳定来源时先无损卸载；`read_file`、`open_kb_document` 已有原始来源，工具执行阶段只使用配置上限分页，最终模型调用前再按总体超额量压缩，不能再次卸载形成复制链路。
10. **不继续依赖 DeepAgents 摘要私有实现。** 当前 Yuxi 子类直接访问 `_lc_helper._trigger_clauses` 等私有字段，无法稳定承载最终请求预检、多轮收敛、私有 revision 和原子提交；重构为项目自有 `AgentMiddleware`，只复用公开消息类型、backend protocol 和 Token 工具，不修改虚拟环境源码。

## 5. 架构与数据边界

系统将会话数据分为两层：

```text
完整历史账本
  PostgreSQL Message / ToolCall
  /outputs/conversation_history
  /outputs/large_tool_results
          │
          ▼
有界模型工作集
  私有滚动摘要
  最近完整交互段
  当前用户输入
  按需读取的历史片段
          │
          ▼
模型请求
```

### 5.1 完整历史账本

- 用户和助手可见消息继续由 PostgreSQL `Message` 保存。
- 小型工具结果由 PostgreSQL `ToolCall.tool_output` 保存完整内容。
- 大型工具结果成功卸载后，`/outputs/large_tool_results/<tool_call_id>-<content_hash>.txt` 是完整结果的权威来源，`ToolCall.tool_output` 只保存路径、预览和状态回执；当前聊天持久化发生在文件/摘要中间件处理之后，不能假设数据库还保存卸载前原文。
- 需要从 checkpoint 移除但尚未确认持久化的 LangChain 消息，先写入 `/outputs/conversation_history`。
- 大型工具结果使用现有 `/outputs/large_tool_results`。
- 文件写入使用内容哈希或稳定 run/message 标识，保证重复压缩不会重复制造数据。

### 5.2 有界模型工作集

工作集仅包含：

- 私有滚动摘要；
- 尚未归档的最近完整交互段；
- 当前用户输入；
- 本轮明确读取的文件或历史片段引用；
- 未完成的工具调用协议消息。

旧消息被裁剪后仍存在于完整历史账本，不再依赖 checkpoint 承担永久消息存储职责。

## 6. 跨模型预算契约

### 6.1 统一模型限制

Chat 模型运行前必须解析出：

| 字段 | 含义 | 来源优先级 |
| --- | --- | --- |
| `context_window` | 模型完整上下文窗口 | 模型配置 `context_length` → LangChain profile |
| `min_output_reserve_tokens` | 压缩输入前必须保留的最低输出空间，不限制实际生成 | 模型配置 → 部署级默认值 → LangChain profile |
| `context_safety_tokens` | 协议和计数误差缓冲 | 模型配置 → 部署级默认值 |

约束：

```text
context_window > min_output_reserve_tokens + context_safety_tokens
```

远程模型接口能返回相关值时自动填充；无法返回时由管理员按实际部署配置。运行时不根据模型名称、参数规模或“32K/128K”等字符串猜测。

预算层只接收一个不可变的标准化结果，避免 `summary.py`、`token_usage.py` 和前端各自解析字段：

```text
ResolvedContextBudget
  context_window: int
  min_output_reserve_tokens: int
  effective_output_reserve: int
  context_safety_tokens: int
  prompt_budget: int
  counter: exact | approximate
```

在 `token_usage.py` 提供唯一的 `resolve_context_budget(ModelRequest, ModelInfo) -> ResolvedContextBudget` 和最终请求计数入口；摘要中间件和指标中间件必须调用同一实现。若窗口缺失，或 `prompt_budget <= 0`，在调用模型前抛出带模型 spec 和缺失字段的配置错误。

现有模型数据按以下发布流程处理，而不是静默套用 70%：

1. 对 provider 能发现的字段执行一次现有 JSON 配置内的幂等回填。
2. 发布前扫描全部启用 Chat 模型，列出缺少 `context_window` 的模型并阻止启用/调用。
3. 管理员为无法自动发现的本地模型补齐真实部署限制；最低输出预留和安全缓冲均可继承部署默认值。
4. `context_safety_tokens` 可使用统一部署默认值，但保存和运行指标中必须展开为实际 Token 数；它不是模型窗口的百分比。

### 6.2 最低输出预留

```text
effective_output_reserve =
    max(本次显式 max_tokens, 模型或部署默认的 min_output_reserve_tokens)
```

不同 SDK 使用 `max_tokens`、`max_completion_tokens` 等名称时，只在 provider 适配边界转换。模型配置的预留不会传入实际请求；若调用方显式限制输出，预算层按更大的值预留，避免真实请求上限超过压缩预留。

### 6.3 输入预算

```text
prompt_budget
  = context_window
  - effective_output_reserve
  - context_safety_tokens

fixed_overhead
  = system prompt tokens
  + active tool schema tokens
  + provider protocol overhead estimate

working_budget
  = prompt_budget - fixed_overhead
```

最终必须满足：

```text
rolling_summary
+ recent_interactions
+ current_input
+ retrieved_context
<= working_budget
```

若 `fixed_overhead >= prompt_budget`，说明 Agent 配置本身不适合该模型，应在调用前报告具体的 system/tool 占用，而不是静默移除工具。

### 6.4 Token 计数器解析

计数器按能力选择，不按模型名选择：

1. 模型对象提供可靠的消息 Token 计数能力时优先使用。
2. 否则使用当前 LangChain `count_tokens_approximately`。
3. 工具 Schema 必须作为同一次计数的输入。
4. 成功响应中的真实 `usage.input_tokens` 用于观测估算偏差，但不能替代调用前计数。
5. 多模态 block 若计数器不能准确估算，旧图片或二进制内容必须外置，只在工作集中保留引用和结构化描述。

`context_safety_tokens` 是部署校准旋钮，用于覆盖不同 Tokenizer、消息模板和推理网关的偏差；不得在代码中为某个模型名称增加特殊余量。

### 6.5 工具结果预算

当前 `DEFAULT_TOOL_RESULT_EVICTION_K_TOKENS = 3` 经过 `* 1024` 后形成 3072 Token 阈值，DeepAgents 再使用 `4 字符≈1 Token` 判断是否超过 12,288 字符。该值只能继续作为单个工具结果的产品级最大内联上限，不能证明小窗口模型的下一次请求安全，也不能准确估算中文内容。

`BaseContext` 正式增加管理员字段 `tool_token_limit: int`，单位为 K Token，默认 3。该字段只表示单个工具结果的最大内联上限；主 Agent 和子 Agent 统一换算为 `tool_token_limit * 1024`，不再使用不存在于 context schema 的 `getattr` 隐式配置。

工具结果采用两阶段处理，但只有第二阶段承担上下文安全责任：

#### 第一阶段：工具返回时快速保护

```text
early_inline_limit
  = configured_tool_inline_cap
```

- 明显超过配置上限的普通工具结果立即卸载，避免先写入 LangGraph state。
- 工具 wrapper 此时拿不到下一次最终 ModelRequest，不能声称已经知道 system、tools、摘要和其他消息的最终占用，也不能用模型级 `prompt_budget` 推导本次“剩余工具预算”。
- 判断使用统一 Token counter；只有 counter 不可用时才使用字符近似，并由模型安全缓冲覆盖估算误差。
- `configured_tool_inline_cap` 保留当前 3K 默认值，但只表示产品希望单个工具最多直接占用多少输入，不表示模型安全边界。

#### 第二阶段：模型调用前权威校验

```text
prompt_deficit_tokens
  = max(0, final_prompt_tokens - prompt_budget)
```

- 摘要中间件在下一次模型调用前根据最终 system、tools、摘要和全部消息计算总体超额量。
- `prompt_deficit_tokens > 0` 时，按 Token 从大到小选择尚未卸载的普通 ToolMessage，卸载一个后重新组装和计数，直到合规或没有普通结果可卸载。
- 对已有稳定源文件及 continuation 的窗口结果，不复制文件；需要继续收缩时把旧窗口替换为包含原始来源、请求范围和重新读取方法的紧凑回执。
- 工具结果处理后仍超预算，再进入最老完整交互段摘要和单条超长输入外置流程。
- 第二阶段是上下文安全的权威判断；第一阶段只是减少无效状态写入。

## 7. 预算驱动的压缩算法

`YuxiSummarizationMiddleware` 改为直接实现项目自有 `AgentMiddleware`，不再继承 DeepAgents `SummarizationMiddleware`。`create_summary_middleware` 移除 `trigger`、`keep` 和 `trim_tokens_to_summarize` 参数，只接收摘要模型、提示词、backend factory 和工具结果配置；同步/异步 wrapper 共用同一纯决策核心，IO 部分分别 await/调用。

内层 `TokenUsageMiddleware` 可能返回携带 `Command(update={"token_usage": ...})` 的 `ExtendedModelResponse`。摘要中间件在主模型成功后增加私有摘要和消息裁剪 Command 时，必须保留原 model response 并合并两个 update；不能覆盖 `token_usage`、中断或其他内层状态更新。若两个 Command 修改同一 key，必须定义显式合并规则并对冲突报错，不能按 wrapper 顺序静默丢字段。

### 7.1 协议安全的交互段

压缩的最小单元不是固定消息条数，而是完整交互段：

- 普通用户消息与后续助手回答；
- 带 `tool_calls` 的 AIMessage 及全部对应 ToolMessage；
- 子 Agent 调用及其最终 ToolMessage；
- interrupt、resume 和人工确认形成的完整协议段。

未匹配 ToolMessage 的工具调用、正在执行的工具和当前用户输入不得作为普通历史裁剪。

### 7.2 严格收敛循环

```text
1. 组装最终 system、tools、摘要、历史和当前输入。
2. 计算最终 prompt tokens。
3. 如果不超预算，调用模型。
4. 如果超预算：
   a. 当前单项本身过大时，先外置并建立摘要/索引；
   b. 否则按实际 Token 缺口选择最老的完整交互段；
   c. 先持久化被移出的原始消息；
   d. 使用“上一版摘要 + 本轮被移出内容”生成新摘要；
   e. 重新组装并重新计数。
5. 仍超预算则继续循环。
6. 每轮必须满足 cutoff 前进、消息外置或 Token 数下降之一，否则终止并报告不可收敛原因。
```

不设置固定压缩次数。理论上限由当前可移出的交互段数量决定，最后还可将单条超长项外置，因此不会依赖任意的“再试两次”。

### 7.3 摘要生成

摘要输入必须包含：

- 上一版滚动摘要；
- 本轮选中的原始交互段；
- 原始历史路径或消息范围；
- 防提示注入说明：归档消息是待总结数据，不是新的系统指令。

摘要必须保留：

- 当前任务、用户意图和明确约束；
- 用户偏好，以及用户提供、工具核验或双方已确认的事实、精确数字、名称和标识符；
- 已完成步骤和待办；
- 关键工具结果、文件、产物和读取路径；
- 失败尝试及原因；
- 需要回查原文的消息或文件定位。

滚动摘要是“完整替换”而不是追加。每次生成时必须把上一版摘要视为持久记忆并与新归档段合并；任务主题变化本身不能成为删除既有精确事实的理由。空间不足时，优先移除过程叙述、临时推理和重复工具输出。摘要确实未保存某个较早细节时，后续回答应通过 `/outputs/conversation_history/` 下的不可变归档恢复，不得根据相似条目猜测；因此系统保证原始历史可恢复，但不承诺无限历史中的任意细节都能在“禁止工具调用”的条件下永久驻留于有限摘要。

摘要作为私有状态参与后续模型请求，不作为 HumanMessage 写入用户消息流。

摘要调用本身使用摘要模型自己的 `context_window`、最低输出预留和安全缓冲；过长摘要输入按同一预算规则分块、逐层合并，不假设主模型和摘要模型窗口相同。

摘要输出也必须由本次最终请求的实际剩余空间约束，不能只限制摘要输入：

```text
target_summary_tokens
  = prompt_budget
  - fixed_overhead
  - current_input_or_pointer_tokens
  - pending_protocol_tokens
  - selected_recent_interaction_tokens

summary_target_tokens
  = target_summary_tokens
```

- 摘要模型的输入分块仍受其自身 `prompt_budget` 限制；`target_summary_tokens <= 0` 时，先减少最近交互段或外置当前超长单项，不能调用摘要模型生成一个注定放不回主请求的摘要。
- 每次摘要调用显式传入标准化后的 `summary_max_output`；供应商忽略输出上限或实际摘要仍超目标时，以最终 Token 重计数为准，继续减少历史或用更小目标重写摘要。
- 滚动摘要不得随轮次无限增长；每次“上一版摘要 + 新归档段”合并后都重新受当前 `target_summary_tokens` 约束，而不是在旧摘要后追加文本。

### 7.4 摘要失败

执行顺序必须为：

```text
原始消息持久化成功
→ 尝试生成摘要
→ 主模型调用成功
→ 提交摘要状态和 checkpoint 裁剪
```

摘要调用失败时：

- 没有可用紧凑表示时，不提交新 cutoff，也不删除原工作消息；
- 保留已写入的幂等历史文件；
- 返回可观测的摘要失败状态；
- 下次调用可以重新尝试。

只有在“原始消息已经安全外置，但摘要模型暂时不可用”的情况下，才允许生成确定性清单继续：角色、消息 ID、时间、文件路径和短预览。该清单是合法但低质量的 `degraded` 紧凑状态，不能伪装成语义摘要成功。

状态提交规则统一为：

```text
原始消息持久化成功
→ 生成语义摘要或 degraded 确定性清单
→ 用紧凑候选调用主模型
→ 主模型成功
→ 原子提交 context_summary、context_compacted_through、context_revision 和 messages Overwrite
```

因此 degraded 路径在主模型成功后必须提交 cutoff，否则下一轮会再次加载同一批超预算消息。主模型失败时，不提交语义摘要或 degraded 状态。

### 7.5 供应商仍报告上下文溢出

即使调用前计数满足预算，供应商仍可能因消息模板或 Tokenizer 差异拒绝请求。处理方式：

1. 将异常标准化为 `ContextOverflowError`。
2. 不进入普通 ModelRetry。
3. 回到压缩循环，再移出一个实际完整交互段或外置最大单项。
4. 使用新候选重新计数并调用。
5. 没有任何可缩减内容时，报告模型限制或配置不一致，但保持会话状态可继续修改配置或发送更短请求。

供应商溢出后的每次收缩量由实际请求和下一个可安全移除的完整交互段决定，不引入固定 5% 尾部兜底。

标准化按“错误能力”而不是模型名称判断：优先识别原生 `ContextOverflowError`；其次识别供应商结构化错误码（如 context length/max input 类 code）；最后仅在非瞬时 400/413 响应中匹配受控的上下文超限文本。普通 400、鉴权、内容审核和参数错误不得误判为可压缩错误。`finish_reason=length` 只有在没有可见正文、没有 tool call，且响应表明生成前已耗尽窗口时才转为上下文溢出；已有可见正文的 length 表示输出达到上限，应作为正常截断响应处理。

## 8. 超长单项处理

### 8.1 超长用户输入

当当前用户消息本身超过 `working_budget`：

1. 用户可见原文仍由现有消息存储保存。
2. 将原文写入当前线程文件后端。
3. 按当前摘要模型的有效输入预算切块，不按固定字符数切块。
4. 为分块生成带偏移量的摘要索引。
5. 工作消息替换为：原始路径、总长度、分块索引、摘要和读取说明。
6. 模型需要精确内容时通过现有 `read_file`/`grep` 读取；单行超长内容维持当前按行截断行为。

当前阶段不修改 API 请求体和 AgentRun 表结构；若存储压力测试证明大型 query 的 JSON 副本成为瓶颈，再单独调整为按 `input_message_id` 加载。

### 8.2 大型工具结果

工具结果按是否已有稳定原始来源分为两类。

#### 8.2.1 普通工具大结果

对于数据库查询、来文结构化结果、MCP 返回值、子 Agent 结果等没有可供模型直接分页读取的结果，复用现有 `/outputs/large_tool_results`：

- 工具返回阶段使用正式配置的 `configured_tool_inline_cap` 快速判断，模型调用前再按 `prompt_deficit_tokens` 做总体收敛；
- 完整结果先持久化到下述稳定的 tool-call + 内容哈希路径；
- ToolMessage 仅保留工具名、结果路径、实际/估算 Token、短预览和读取说明；
- 已外置结果带稳定标记，避免后续上下文整理再次写出相同内容；
- 写入成功后，文件是完整结果的权威来源，PostgreSQL ToolCall 保存路径和预览回执；
- 写入失败时不得把超预算原始 ToolMessage 继续传给模型，应返回有界的结果持久化错误并将 ToolCall 标记为失败；由于原始结果未成功持久化，不声明其可恢复，允许 Agent 或用户重新执行工具；
- `Command` 中包含多个 ToolMessage 时逐个计算，不能只按总字符串长度截断整个 Command；重建 Command 时必须原样保留 `goto`、`graph` 和除 `messages` 外的全部 update，不能因卸载结果丢失工具的业务状态更新。

不能直接依赖 DeepAgents 当前私有 `_process_large_message` 作为最终实现：它用 `4 字符≈1 Token` 判定，且写入失败（包括同路径已存在）时会把原始大消息原样返回。项目应在 `YuxiFilesystemMiddleware` 中实现同步/异步共用语义的自有处理函数，使用统一 Token counter，并采用以下稳定路径：

```text
/outputs/large_tool_results/<sanitized_tool_call_id>-<content_sha256_prefix>.txt
```

内容哈希使同一 tool call 的同一结果可幂等复用、不同结果不会误读旧文件；`already exists` 只有在哈希路径一致时视为成功。工具返回阶段成功卸载后，替换 ToolMessage 进入 checkpoint，后续 `chat_service._save_tool_message` 持久化同一回执。模型调用前才因总体缺口卸载的历史 ToolMessage，也必须通过主模型成功后的 state Command 一并替换，确保 checkpoint 和聊天持久化看到相同回执；主模型失败时只允许留下可回收的幂等文件，不提交消息替换。

`read_incoming_document(include_full_text=false)` 返回的结构化结果适用本规则；结果较大时卸载完整 JSON/文本表示，模型收到路径和预览。

#### 8.2.2 已有源文件的窗口读取

`read_file`、`open_kb_document` 不适用二次卸载：

- 原文件、知识库文件已经是稳定数据源，再写入 `large_tool_results` 只会复制内容，并可能形成“读取 → 卸载 → 再读取”的循环；
- 保留 `_TOOL_RESULT_EVICTION_EXEMPT_TOOLS`，但该豁免仅表示免于二次文件卸载，不表示免于预算限制；
- 工具内部只按 `configured_tool_inline_cap` 限制单次窗口；模型调用前的总体预算仍由摘要中间件负责；
- `open_kb_document` 的 `window_size` 是行数，不能用固定“行数→Token”换算。工具先取得请求窗口，再用统一 counter 选择配置上限内最大的完整行前缀，并据此重算 `end_line`、`next_offset` 和 `has_more_after`；若第一行自身已超过配置上限，则返回包含知识库、文件和行号的有界来源回执，不返回超预算内容，也不承诺行内 continuation；
- 上游 `read_file` 只有行级 `offset/limit`，`ReadResult` 不提供总行数或 `has_more`，不能在方案中承诺精确 `has_more`；普通行级读取继续返回路径、请求 offset/limit 和截断提示；
- 模型调用前若源文件窗口仍导致超预算，只把历史 ToolMessage 替换为紧凑读取回执，不生成第二份 `large_tool_results` 文件。

`read_incoming_document(include_full_text=true)` 已经把附件 Markdown 写入线程 sandbox 并只返回 `markdown_files`，维持当前路径回执契约，不把全文填回 ToolMessage，也不在工具边界自动摘要。

#### 8.2.3 摘要边界

- 工具返回阶段不自动用 LLM 摘要整个文件；当前模型只获得有界窗口或文件回执。
- 用户明确要求总结整份文档时，由 Agent 分页读取并执行分块总结，这是业务任务，不是上下文中间件的隐式行为。
- 工具交互成为旧历史后，滚动摘要只保留已确认结论、读取目的、待核验事项和原始路径，不把完整内容重新填回原 ToolMessage。

### 8.3 多模态内容

- 当前模型明确支持多模态且内容能放入预算时，当前轮可保留原始 block。
- 旧图片、Base64 和二进制 block 不在历史中重复内联，改为文件引用、已有描述和必要元数据。
- 不支持多模态的模型不得收到未转换的多模态 block。
- 不为具体视觉模型名称编写分支，能力从模型 profile 和消息类型解析。

## 9. 中间件顺序与异常职责

LangChain 中间件列表中第一个 wrapper 是最外层。目标顺序为：

```text
文件系统 / 附件 / Skills / TodoList / PatchToolCalls / 动态工具与子 Agent 工具过滤等请求修改器
→ YuxiSummarizationMiddleware
→ TokenUsageMiddleware
→ ModelRetryMiddleware
→ Model
```

列表第一个 wrapper 是最外层，因此所有可能改变 system prompt、tools 或 messages 的 middleware 必须位于摘要中间件之前。当前主/子图把 `TodoListMiddleware`、`PatchToolCallsMiddleware`，以及子 Agent 的 `_SubAgentToolFilterMiddleware` 放在摘要之后，摘要看到的不是最终 request；实施时必须调整顺序，并用记录型 Fake Model 断言摘要计数与模型实际收到的 system/tools/messages 完全一致。仅声明“计算最终 request”而不重排现有列表是不成立的。

职责如下：

### `YuxiSummarizationMiddleware`

- 获取最终 request 的 system、tools 和 messages；
- 解析模型预算；
- 执行压缩收敛循环；
- 捕获并处理 `ContextOverflowError`；
- 生成私有摘要状态和 checkpoint 更新。

### `TokenUsageMiddleware`

- 记录最终成功候选的输入构成；
- 识别 OpenAI 兼容服务的空正文 `finish_reason=length` 并转为标准上下文异常；
- 不决定压缩比例和保留消息。

### `ModelRetryMiddleware`

只重试超时、连接错误、429 和明确可重试的 5xx：

```text
retry_on = transient_error_predicate
on_failure = "error"
```

`ContextOverflowError` 必须排除。提交 `1e97605c9a0e75e63b01fdab1eb03158c8b9b25d` 中 TokenUsage 位于 ModelRetry 外层的顺序可以保留，但必须同时收紧 ModelRetry 的异常范围；单独调整顺序不能解决直接供应商异常被转换为 AIMessage 的问题。

主 Agent 和子 Agent 必须通过同一个 `create_summary_middleware` 工厂获得完全相同的预算和恢复逻辑，图构建文件只传模型、提示词和工具结果限制，不重复实现策略。

## 10. LangGraph 状态与并发

### 10.1 私有上下文状态

在 Agent state 中增加最小私有字段：

```text
context_summary
context_summary_quality
context_compacted_through
context_archive_path
context_revision
```

- `context_summary` 是私有摘要文本；`context_summary_quality` 仅允许 `semantic` 或 `degraded`。
- `context_compacted_through` 保存最后一个已完整归档交互段的稳定 message ID，不保存易随列表裁剪变化的数组下标。
- `context_archive_path` 指向本 revision 的不可变 JSONL 清单；文件名包含 revision 和归档消息 ID 范围。普通未外置消息在条目中保存完整可序列化内容；已有 PostgreSQL/`large_tool_results` 权威来源的大内容保存来源标识、路径、角色、message/tool-call ID 和哈希，避免再复制一份全文。
- `context_revision` 从 0 单调递增，用于将归档清单和当前摘要状态关联；它不是 LangGraph checkpoint 的条件写入版本号。
- 归档消息若没有稳定 ID，在归档清单中生成由 revision、段内序号和内容哈希组成的确定性 archive ID；保留消息缺少 LangGraph ID 时在最终 surviving list 中补齐。

Token 指标继续使用现有 `token_usage`。不在 state 保存无限增长的 archive path 列表；全部不可变清单统一位于固定会话目录，可通过 `ls/read_file` 和 revision/消息 ID 定位。

### 10.2 物理裁剪 checkpoint

主模型成功后，使用 `Overwrite(surviving_messages)` 原子替换 messages channel，而不是对可能缺少 ID 的旧消息逐个发送 `RemoveMessage`。这与 DeepAgents 当前为避免 DeltaChannel replay 产生重复消息而使用 Overwrite 的原因一致。必须验证：

- 历史消息 API 使用 PostgreSQL，而不是依赖 checkpoint 渲染用户历史；
- 删除不会破坏 ToolCall/ToolMessage 配对；
- 删除后 checkpoint 序列化大小和活跃消息 Token 数都保持有界；
- 服务重启后摘要和最近消息能够继续工作。

### 10.3 同线程并发

同一 `checkpoint_thread_id` 只能有一个运行写入上下文状态。复用现有 PostgreSQL，采用“创建期行锁 + 执行期 advisory lock”，不新增锁服务，不使用只能保护单进程的 `asyncio.Lock`，也不引入需要猜测模型时长的 Redis TTL/心跳锁。

```text
创建期：SELECT Conversation ... FOR UPDATE
执行期：pg_try_advisory_lock(stable_int64(checkpoint_thread_id))
```

- `agent_run_service.create_agent_run` 先在同一事务内锁定已验证归属当前用户的 Conversation 行，再按 request-id 做幂等返回，并查询同一 `checkpoint_thread_id` 是否存在 `pending/running/cancel_requested` run。
- 已有活动 run 时返回 `409` 和活动 `run_id`，且不得新增第二条用户消息或 AgentRun；`interrupted` 不代表仍在写 checkpoint，合法 resume 可在校验 parent 后创建。
- 活动检查、AgentRun 创建和用户消息创建必须位于同一数据库事务和同一会话行锁内，使多 API 进程上的并发请求也串行化。入队失败时把已创建 run 标为明确失败；不回滚已经作为失败尝试保存的用户消息。
- `run_worker.process_agent_run` 在进入 `stream_agent_chat/resume` 前，使用独立且专用于锁生命周期的 PostgreSQL 连接获取 session-level advisory lock；失败则不调用 Agent、不写 checkpoint，并作为可重试队列冲突处理。
- advisory key 由完整 `checkpoint_thread_id` 经过固定、跨进程一致的 64-bit 哈希得到，不使用 Python 进程随机化 `hash()`；哈希碰撞最多串行化不同线程，不能造成并发写入。
- advisory lock 在整个模型/工具流期间由同一连接持有，在 `finally` 显式释放；worker 崩溃或数据库连接断开时 PostgreSQL 自动释放，不依赖 TTL。
- `context_revision` 只记录已提交的归档版本。LangGraph 的普通 state update 没有可供中间件使用的条件写入接口，不能把一次普通读取后比较伪装成乐观锁；创建期行锁和执行期 advisory lock 才是并发写入的强制边界。

验收要求：同一 `checkpoint_thread_id` 的第二个请求稳定得到 `409`，幂等重试仍返回原 run；即使 API 进程或 worker 异常退出，PostgreSQL 也会释放 advisory lock，后续运行不会永久阻塞线程。

### 10.4 旧 checkpoint 处理

本项目当前处于开发阶段，本次实施直接采用“备份后清理旧 checkpoint”，不再保留待选迁移分支：

1. 部署前备份 checkpoint 数据。
2. 停止或等待现有运行完成。
3. 预检当前 Docker API/Worker 实际使用 `AsyncPostgresSaver`；若仍回退 SQLite/InMemory，停止发布并先修复 checkpointer 配置，不能用另一套存储的清理结果冒充成功。
4. 对 PostgreSQL `checkpoints`、`checkpoint_blobs`、`checkpoint_writes` 做可恢复备份；保留 `checkpoint_migrations`。
5. 从 `checkpoints` 枚举去重后的精确 `thread_id` 清单，输出清单数量和备份位置，再逐个调用 checkpointer 的 `adelete_thread(thread_id)`；禁止直接清空数据库、删除持久卷或使用未解析通配符。
6. 验证三个 checkpoint 数据表的目标 thread 均为 0，并抽样确认备份可读。
7. 保留 PostgreSQL 用户可见历史、AgentRun、ToolCall 和线程文件，并对清理前后计数/校验值。

- [ ] `AC-19` 4K 模型即使每个 ToolMessage 都小于 3K，只要最终请求总体超预算，也会依据 `prompt_deficit_tokens` 卸载最大的普通结果并重新计数。

- [ ] `AC-21` `open_kb_document` 对完整行保留精确 continuation；单行超长内容返回有界来源回执；`read_file` 保留按行范围提示；两者都不生成第二份 `large_tool_results` 文件。
- [ ] `AC-22` 普通工具结果卸载成功后，线程文件保存完整原文，PostgreSQL ToolCall 和 ToolMessage 只保存一致的路径/预览回执；写入失败时 ToolCall 明确失败且主模型收不到超预算原文。
- [ ] `AC-23` 线程 A 不能通过回执或路径逃逸读取线程 B 的归档、工具结果或源文件。

### 发布与并发

- [ ] `AC-24` 同一 `checkpoint_thread_id` 的第二个非幂等请求得到 `409` 且不新增用户消息；相同 request-id 重试仍返回原 run。
- [ ] `AC-25` 多 API 进程并发创建由 Conversation 行锁串行化；advisory lock 获取失败的 worker 不调用 Agent，worker 异常或连接断开后 PostgreSQL 自动释放执行锁。
- [ ] `AC-26` 部署前检查能列出所有缺少上下文窗口的启用 Chat 模型，并阻止它们进入模型调用。

## 15. 测试矩阵

### 单元测试

- 预算公式、字段优先级和配置校验。
- 消息协议分组和 cutoff 选择。
- 摘要多轮收敛和严格进展判断。
- 摘要模型输入分块和 `target_summary_tokens` 输出约束，包括目标为 0、供应商返回超目标文本和旧摘要重写。
- 上一版摘要合并。
- 大型 ToolMessage 外置和幂等路径。
- 多 ToolMessage Command 卸载后保留非 messages update、goto 和 graph。
- `prompt_deficit_tokens` 在多个单项均低于配置上限、但总请求超预算时仍能按最大结果优先收敛。
- 中文工具结果不能依赖四字符近似通过最终预算校验。
- `read_file`、`open_kb_document` 的范围/continuation 契约及源文件窗口不发生二次卸载；覆盖知识库首行单独超过配置上限时返回来源回执的情况。
- 普通结果卸载写入失败时关闭超预算调用路径。
- 语义摘要失败后的 `degraded` 清单只有在主模型成功后才提交；失败候选不推进 cutoff。
- 不同模型 profile 与 counter 能力。
- 异常分类和 Retry predicate。
- Conversation 行锁内的活动 run 检查、幂等重试，以及 advisory key 稳定性、获取失败、显式释放和断连自动释放。

### 集成测试

- 主 Agent 和子 Agent 使用相同上下文策略。
- 流式与非流式请求都不泄漏摘要。
- PostgreSQL 消息、ToolCall 和 LangGraph state 更新顺序。
- checkpoint 裁剪后历史 API 仍返回完整可见消息。
- 同线程并发请求 409、同 request-id 幂等、worker advisory lock 冲突不进入 Agent 和 revision 冲突。
- 线程 A 访问线程 B 的归档/工具结果/源文件时被拒绝，`..` 和绝对宿主路径不能逃逸 sandbox。
- 归档内容包含伪 system prompt 或工具指令时只被当作摘要数据，不改变摘要系统指令。

### E2E 与压力测试

- 小窗口 Fake Model：精确触发多次压缩和供应商溢出。
- 长会话：至少 1000 轮合成消息，检查 checkpoint 大小曲线。
- 工具密集：连续产生大型结果并分页回读。
- 小窗口工具结果：4K profile 下构造多个各自小于 3K、合计超过输入预算的结果，验证最终请求按总体缺口卸载。
- 跨语言工具结果：使用等字符数中文和英文内容验证 Token 计数与安全缓冲。
- 源文件回读：重复分页 `read_file`/`open_kb_document`，验证不产生嵌套卸载文件。
- 卸载故障：模拟线程文件写入失败，确认主模型未收到完整超预算 ToolMessage。
- 单条长输入：超过模型窗口后仍能基于索引回答和回查。
- 多模态历史：旧图片不重复内联。
- 服务重启：API、Worker 和 checkpoint 恢复后续聊。
- 开发数据迁移：备份并清理目标旧 checkpoint 后，验证 PostgreSQL 历史、ToolCall 和线程文件数量/校验值不变。
- 真实本地模型：至少覆盖两个不同窗口或不同最低输出预留配置，不以模型名称作为验收条件。

## 16. 可观测性

每次模型调用记录结构化调试信息，不记录用户全文：

```text
model_spec
context_window
prompt_budget
estimated_prompt_tokens
actual_input_tokens
system_tokens
tools_tokens
configured_tool_inline_cap
prompt_deficit_tokens
tool_result_tokens
offloaded_tool_result_count
source_window_receipt_count
summary_tokens
recent_tokens
compaction_count
compaction_reason
overflow_recovery_count
context_revision
thread_lock_outcome
counter
```

需要关注：

- 估算值与真实 `input_tokens` 的偏差；
- 中文与英文 ToolMessage 的估算偏差及最终 counter 类型；
- 最终请求产生总体 Token 缺口的次数、缺口大小和每次外置后的下降量；
- 普通结果卸载失败次数和源文件窗口二次卸载次数（后者必须为 0）；
- 每轮摘要前后 Token 下降量；
- 同一模型频繁发生供应商溢出时是否需要调整该模型安全缓冲；
- checkpoint 序列化体积是否随轮数保持平台期；
- degraded 摘要是否出现及其原因。
- checkpoint-thread 行锁等待、活动 run 冲突、advisory lock 获取失败/释放和 revision 冲突次数。

## 17. 发布、回滚与数据安全

### 发布前

1. 等待正在运行的 AgentRun 完成。

3. 确认 PostgreSQL 消息和 ToolCall 数量。
4. 确认线程文件目录可读写。

1. 运行健康检查和短对话冒烟测试。
2. 运行小窗口强制压缩测试。
3. 运行工具密集和超长输入测试。
4. 重启服务后续聊同一线程。
5. 观察上下文溢出、摘要失败和 checkpoint 大小。

### 回滚

- 代码通过 Git 回滚。
- checkpoint 状态契约不兼容时恢复发布前备份。
- PostgreSQL 用户消息、ToolCall 和线程文件不因代码回滚删除。
- 不执行无法恢复的历史清理；旧 checkpoint 清理必须在备份验证后单独授权。
