# 文档解析后端调研与旧格式修复

## 目标与范围

- 评估 Docling、MinerU 与专用 OCR 按文件格式组合使用是否合理。
- 修复 `.doc` 无法上传、`.xls` 被直接交给不支持该格式的 Docling 的问题。
- 不重构现有 OCR 工厂，不新增解析服务或 Python 依赖。

## 验收标准

- [x] `.doc` 出现在后端支持格式中。
- [x] `.doc/.xls` 先转为 `.docx/.xlsx`，再进入现有 Docling 链路。
- [x] API 镜像具备 Word 与 Excel 的 LibreOffice 无头转换组件。
- [x] 解析器单元测试与 Ruff 检查通过。
- [ ] 在重建的 API 容器内用真实 `.doc/.xls` 样本完成端到端验证。

## 调研结论

Docling 与 MinerU 的当前官方输入格式都覆盖 PDF、图片和现代 Office 格式，但不覆盖二进制 `.doc/.xls`。因此，以 Docling 作为所有格式的单一后端并不能消除旧格式适配；更合适的边界是先用 LibreOffice 做确定性的格式升级，再交给 Docling。

现有“按文档特征选择实现”的方向合理，但应区分两层：常规文本和现代 Office 使用轻量本地解析，复杂 PDF/扫描件才按用户选择调用 MinerU、PP-Structure 或其他 OCR。多个 OCR 实现是能力与部署成本的选择，不应成为同一种普通 Office 格式的随机回退链。

## 实现决策

保留现有统一 `Parser` 入口，只增加一个旧 Office 转换函数；`.doc/.xls` 转换成功后继续使用同一个 Docling Markdown 输出路径。这样修复位于所有调用方共享的格式路由处，且不引入新的抽象。

## Docker 镜像依赖

旧 Office 转换与 Office 文件 PDF 预览都依赖容器内的 LibreOffice 命令行工具，因此 `docker/api.Dockerfile` 中按格式拆装了三个无 GUI 模块，避免拉入完整套件：

| 包名 | 负责格式 | 用途 |
|------|---------|------|
| `libreoffice-writer-nogui` | `.doc` / `.docx` | 旧 Word 文档升级为 Docling 可识别的现代格式 |
| `libreoffice-calc-nogui` | `.xls` / `.xlsx` | 旧 Excel 文档升级；本任务为支持 `.xls` 解析而新增 |
| `libreoffice-impress-nogui` | `.ppt` / `.pptx` | 演示文稿转换（入库侧、预览侧均可能触发） |

三处实际调用点：

- 知识库入库：[backend/package/yuxi/knowledge/parser/unified.py:173](backend/package/yuxi/knowledge/parser/unified.py#L173) 在解析前对 `.doc` / `.xls` 做格式升级。
- 文件 PDF 预览：[backend/package/yuxi/services/file_preview.py:110-112](backend/package/yuxi/services/file_preview.py#L110-L112) 通过 `soffice` / `libreoffice` 命令将 Office 文件转 PDF。

选择 `*-nogui` 变体是容器场景下的必要约束：无显示器、不会触发图形栈，体积也更小；任何一段调用缺失对应模块都会直接抛错（例如预览侧 `OfficePreviewConversionError`），因此补装时按格式一一对应，而不是统一装 `libreoffice` 全家桶。
