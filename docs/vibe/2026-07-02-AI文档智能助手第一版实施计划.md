# AI文档智能助手第一版实施计划

日期：2026-07-02  
状态：待开发  
关联方案：`docs/vibe/2026-07-02-AI文档智能助手第一版开发方案.md`

## 1. 开发目标

第一版先完成一个可联调的竖切闭环：

```text
生产系统页面附件信息
  -> docMind 匹配 KnowledgeFile
  -> 查询当前 Markdown 对应的结构化抽取结果
  -> chat-iframe 自动展示
  -> 用户继续基于网页、文件或普通聊天追问
```

第一版结构化抽取在 `KnowledgeFile.status = parsed` 且 `KnowledgeFile.markdown_file` 已写入后触发。抽取读取 Markdown 内容并在内存中切分，不依赖 `KnowledgeChunk`，也不提前写入 `knowledge_chunks`。

## 2. 开发原则

- 先打通后端查询和抽取闭环，再做 iframe 页面体验。
- 复用现有 `KnowledgeFile`、Markdown 解析、`tasker`、抽取 schema 和聊天接口。
- `knowledge_business_extraction_items.chunk_id` 保留为可选真实 chunk 关联；Markdown 阶段抽取结果不填该字段。
- 来源元数据第一版写入 `KnowledgeFile.processing_params`，核心字段为 `source_system/source_url/source_key/source_doc_id/source_filename/source_size_text/content_hash/metadata`。
- 第一版不做按文档类型或业务分类的知识库路由，所有来文先进入 docMind 后端配置的来文默认知识库。
- 自动结构化抽取使用后端默认抽取模型；iframe 中的模型选择只影响用户聊天。
- 第一版认证先复用 docMind 现有登录态或 token，短期嵌入 token 作为后续增强。

## 3. 开发顺序

### 阶段一：锁定后端接口契约

目标：让前后端可以并行开发。

任务：

- 定义 `IncomingPageFile` 请求结构，兼容 `url` 和 `sourceUrl`。
- 定义生产系统文档推送接口，优先使用 `POST /api/incoming-documents/ingest`。
- 定义 `/api/incoming-documents/extractions/query` 响应结构。
- 明确 `matchStatus`：`matched/multiple/pending_sync/not_found`。
- 明确 `extractionStatus`：`ready/running/not_found/failed`。
- 明确 `draft` 抽取结果对前端展示为 `ready`。

验收：

- 后端 schema 或 service 类型能表达请求和响应。
- 前端可基于 mock 响应开发展示。

生产系统文档推送接口约定：

- 使用 `POST`，用于提交文件或文件链接并创建处理任务。
- 不使用 `GET` 传文档；`GET` 只用于查询状态或结果。
- 第一版推荐生产系统直接传文件，docMind 收到后立即保存原始文件，避免后续下载链接失效、权限变化或内网互通问题。
- 如果生产系统只能提供链接，则传 `sourceUrl`，由 docMind 后台任务下载；该链接需要在任务处理期间可访问。
- 接口收到请求后只完成参数校验、文件落盘或下载任务创建、`KnowledgeFile` 记录创建，然后返回任务或文件标识。
- Markdown 解析和业务结构化抽取通过 `tasker` 后台任务处理，避免同一时间多个或十几个文档推送时阻塞请求。
- 推送接口必须校验认证、文件类型和文件大小；重复推送同一 `sourceSystem + sourceKey` 时复用已有文件记录或返回已有任务，避免重复入库。

推荐接口：

```text
POST /api/incoming-documents/ingest
```

直接传文件时使用 `multipart/form-data`；只传链接时使用 `application/json`。

第一版最小必传字段：`file` 或 `sourceUrl` 二选一，另传 `sourceKey` 和 `filename`。如果生产系统没有单独的附件 ID，可从下载链接中提取稳定编号作为 `sourceKey`，例如 `202606100417`。

推荐字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `file` | 直接传文件时必填 | 上级下发文档原文件 |
| `sourceUrl` | 传链接时必填 | 生产系统附件下载链接 |
| `sourceKey` | 必填 | 生产系统侧可稳定标识该附件或文档的 ID；可取链接中的 `202606100417` |
| `sourceDocId` | 可选 | 生产系统侧来文或流程主表 ID |
| `sourceSystem` | 可选 | 来源系统命名空间；不传时后端默认 `production`，用于后续多来源系统防止 `sourceKey` 冲突 |
| `filename` | 必填 | 原始文件名；直接传文件时也建议显式传 |
| `fileSize` | 可选 | 文件大小，单位 byte |
| `contentHash` | 可选 | 文件内容哈希，用于同名文件辅助去重；不传时后端可在保存文件后计算 |
| `sourceSizeText` | 可选 | 页面展示大小，例如 `123 KB`；仅用于展示或没有 `fileSize` 时辅助匹配 |
| `title` | 可选 | 来文标题或页面标题 |
| `receivedAt` | 可选 | 生产系统收到上级下发文档的时间 |
| `businessNo` | 可选 | 业务编号、流程编号或收文编号，用于业务追溯和页面展示 |
| `sender` | 可选 | 发文单位或来源部门 |
| `metadata` | 可选 | 其他业务字段 JSON 字符串，例如后续可能出现的 `docType/businessCategory/department` |

目标知识库由 docMind 侧兜底管理。实施前先在 docMind 创建或配置一个“来文默认知识库”；第一版不要求生产系统传 `kbId`，也不根据 `docType/businessCategory/department` 做知识库分流。后续等生产系统可稳定提供业务字段后，再评估是否增加后端路由规则。

直接传文件示例：

```text
POST /api/incoming-documents/ingest
file=@来文文件.docx
sourceKey=202606100417
filename=来文文件.docx
```

传链接示例：

```json
{
  "sourceUrl": "http://ip/xxx/default.ashx?202606100417",
  "sourceKey": "202606100417",
  "filename": "来文文件.docx",
  "sourceSizeText": "123 KB"
}
```

推荐响应：

```json
{
  "fileId": "file_xxx",
  "kbId": "kb_xxx",
  "taskId": "task_xxx",
  "status": "accepted"
}
```

### 阶段二：补齐 Markdown 结构化抽取入口

目标：已有 `KnowledgeFile.markdown_file` 时，不依赖知识库入库也能抽取。

涉及文件：

- `backend/package/yuxi/knowledge/extraction/service.py`
- `backend/package/yuxi/repositories/knowledge_business_extraction_repository.py`
- `backend/package/yuxi/repositories/knowledge_file_repository.py`

任务：

- 新增 Markdown 抽取入口，例如 `run_markdown_extraction(...)`。
- 读取 `KnowledgeFile.markdown_file` 指向的完整 Markdown。
- 短文档作为一个抽取片段，长文档复用现有 `chunk_markdown` 在内存中切分。
- 抽取片段只用于分类和结构化抽取，不写入 `knowledge_chunks`。
- 写入 `knowledge_business_extraction_runs/results/items`。
- `run_metadata` 记录 `markdown_file/model_spec/segment_count/errors`。
- item 写库时 `chunk_id = None`。
- 查询或复用结果时校验 `file_id + markdown_file + model_spec`。

验收：

- 缺少 `KnowledgeChunk` 时仍可完成抽取。
- 同一 `file_id + markdown_file + model_spec` 已有成功结果时可复用。
- 文件重新解析生成新 `markdown_file` 后不会误用旧结果。

### 阶段三：接入解析成功后的后台任务

目标：Markdown 解析完成后自动提交结构化抽取任务。

涉及文件：

- `backend/server/routers/knowledge_router.py`
- `backend/package/yuxi/services/task_service.py`
- `backend/package/yuxi/knowledge/extraction/service.py`

任务：

- 新增任务类型 `knowledge_business_extraction`。
- 在解析编排层调用 `knowledge_base.parse_file(...)` 成功后提交抽取任务。
- 使用 `enqueue_unique_by_payload` 按 `kb_id/file_id/markdown_file/model_spec` 去重。
- 批量解析、待解析文档解析、生产系统推送入库解析成功后走同一触发函数。
- 自动入库开启时，解析成功后提交抽取任务，再继续向量入库。
- 抽取失败不影响文档入库。

验收：

- 手动解析文档后能看到抽取任务进入队列。
- 自动入库时不等待抽取任务完成。
- 重复提交不会产生重复 pending/running 任务。

### 阶段四：实现附件匹配和抽取结果查询

目标：iframe 传入附件后，后端返回匹配状态和结构化结果。

涉及文件：

- `backend/package/yuxi/services/incoming_document_service.py`
- `backend/server/routers/incoming_document_router.py`
- `backend/package/yuxi/repositories/knowledge_file_repository.py`
- `backend/server/main.py` 或现有 router 注册位置

任务：

- 标准化页面附件字段，生成稳定 `incomingFileId`。
- 按优先级匹配 `KnowledgeFile`：
  `source_key/source_url -> source_doc_id + filename -> filename + file_size -> filename`。
- 匹配多份返回 `multiple`。
- 有来源线索但未匹配返回 `pending_sync`。
- 只有文件名且未匹配返回 `not_found`。
- 匹配成功后查询当前 Markdown 对应的最新成功抽取结果。
- 返回 `ready/running/not_found/failed` 展示状态和失败原因。

验收：

- `/api/incoming-documents/extractions/query` 可批量返回多个附件状态。
- `draft` 结果返回 `ready`。
- 最近一次任务失败且没有可用成功结果时返回 `failed`。

### 阶段五：补最小推送入库能力

涉及文件：

- 保存原始文件。
- 创建或更新 `KnowledgeFile`，同一 `source_system + source_key` 重复推送时复用已有记录。
- 写入 `processing_params.source_system/source_url/source_key/source_doc_id/source_filename/source_size_text/content_hash/metadata`。
- 文件保存成功后提交 Markdown 解析任务。

验收：

- 给定一个生产系统附件来源信息，docMind 中存在可匹配 `KnowledgeFile`。
- 重复推送同一 `sourceSystem + sourceKey` 不重复创建文件记录。
- 文件完成 Markdown 解析并自动产生抽取任务。
