## 1. 目标

基于当前来文解析和业务抽取能力，按优先级完成以下产品闭环：

1. **P0：分类纠偏和文档级结果展示**
   - 一份来文及其主文件、附件作为一个业务对象。
   - 自动分类允许从系统已配置分类中纠偏。
   - 页面展示文档级摘要、分类和按抽取类型归并后的结构化结果。
   - 不建设逐条 item 审批系统。
2. **P1：来文查询、读取和统计工具**
   - 按来文时间、分类、条目类型和关键词查询。
   - 读取一份来文的元数据、结构化结果和全部附件。
   - 需要全文时将 MinIO Markdown 写入当前线程 sandbox，返回 `markdown_path`。
   - 提供准确的文档级基础统计。
3. **P2：首批业务 Skill**
   - 单篇来文综合解读。
   - 风险台账生成。
   - 通报、考评、奖惩汇总。
4. **P3：组织关联和细粒度权限**
   - 在客户提供稳定部门、专业、岗位主数据后实施。

### 2.2 Phase 1 改造前的结构性问题

1. `incoming_documents` 实际是一附件一行，不是一份来文一行。
2. 文号、标题、来文类型、发文单位、日期在每个附件上重复保存。
3. 标准业务字段同时存在于独立列和 `metadata_json`，有两份真值。
4. 分类、摘要和正式抽取以附件为处理单位，缺少文档级最终结果。
5. 当前页面按单个 `incoming_id` 查看附件记录，无法自然表达一份来文及全部附件。
6. 人工确认字段已预留，但没有符合当前需求的文档级纠偏和确认流程。
7. Agent 尚无来文查询、读取和统计工具。
8. 尚无围绕客户业务场景的来文 Skill。

## 3. 固定设计决策

### 3.1 不做兼容迁移

- 删除旧 multipart 顶层业务字段：`document_number/title/incoming_type/source_unit/incoming_date`。
- 删除附件表中的同名业务列和旧 `metadata_json` 双写逻辑。
- 更新 chat-iframe、Web、测试和示例代码，不保留旧请求分支。
- 开发环境直接重建来文和业务抽取相关表，不编写历史数据迁移脚本。

### 3.2 来文和附件分表

- `incoming_documents`：一份来文一行，保存文档身份、元数据、文档级处理结果和确认状态。
- `incoming_document_files`：一个主文件或附件一行，保存文件身份、MinIO 地址和文件处理状态。
- 文档级唯一身份：`source_system + source_function_id + source_document_id`。
- 文件级唯一身份：`incoming_id + source_file_id`。

### 3.3 可选业务字段只存 `document_metadata`

- 第一层接入必需字段保持独立列。
- 文号、标题、类型、发文单位、来文日期及以后新增的业务字段统一保存到 `document_metadata` JSONB。
- API 使用 Pydantic 模型校验已知字段，允许额外字段。
- 不为新增业务字段立即增加数据库列。
- P1 直接查询 JSONB 中的稳定键；出现实际性能问题后再增加 JSON 表达式索引。

### 3.4 分类是单一主分类

- `ai_classification` 保存模型原始分类。
- `classification_evidence` 保存支持 AI 主分类判断的逐字原文依据。
- `confirmed_classification` 保存人工纠偏分类。
- 有人工分类时以人工分类为准，否则使用 AI 分类。
- 人工只能从 `DocumentCategoryResult` 已配置分类中选择，不能自由输入。
- 新增分类必须同时定义分类说明、抽取 schema 和显示元数据，属于开发配置，不属于普通用户操作。
- `additional_classifications` 保存附加分类的分类名、独立置信度和逐字原文依据；只有置信度不低于 0.8 且依据能在原文中定位时才保留。
- 正式抽取所需的分类集合在处理时由主分类和有效附加分类即时派生，不重复持久化派生字段；它不改变页面显示的单一主分类。

### 3.5 正式结果按抽取类型归组

- 一份文档的正式结果按 `item_type` 组织为结果组。
- 每个结果组只有一个摘要和一个 details 列表。
- 页面默认展示摘要和第一条 detail，其余 detail 折叠查看。
- 保留多条真实业务事实，不为了界面简洁删除数据。
- 不提供 detail 的人工修改、确认和驳回。

主分类只用于来文展示、筛选和统计；抽取类型由文档级分析从全部附件中选出，不能仅由主分类单向决定。这样主文件与附件侧重点不同，也不会遗漏附件中的风险、任务等事实。

### 3.6 小助手先读来文结论，按需读取附件原文

- 嵌入页默认只对应一份来文；同一页面的主文件和附件共享同一个 `incoming_id`。
- 初始上下文只传递 `incoming_id`、文档级摘要、有效分类、结果组和附件清单；不将任一附件的完整 Markdown 注入提示词。
- 小助手首先回答“这份来文整体讲了什么”，依据文档级摘要和正式结构化结果。
- 仅在用户明确指定附件、追问具体细节、需要核验或需要原文引用时，才定位到对应附件并读取其 Markdown。
- 每条 detail 的 evidence 必须包含 `source_file_id`、文件名、原文引用和可用的标题/条目位置；回答和页面都据此标注来源附件。

### 3.7 全文读取复用 `read_file`

- `read_incoming_document(include_full_text=true)` 负责下载 MinIO Markdown 并写入当前线程 sandbox。
- 默认不下载 Markdown；只有传入指定附件并设置 `include_full_text=true` 时才下载。
- 工具只返回该附件的 `markdown_path`，不返回 `reader_tool`、MinIO URL 或宿主机路径。
- Skill 负责说明何时使用 `read_file` 读取该路径。
- 不新增原始 PDF、Word 的 Agent 读取工具。

### 3.8 超长来文的分层分析

不持久化拼接后的“大 Markdown”，只在任务运行时按附件边界组织输入。

1. 从模型管理中的 `context_length` 计算输入预算，正文最多使用上下文窗口的 70%，其余空间留给系统提示词和结构化输出；模型未配置窗口时按 32K 处理。
2. 所有附件 Markdown 总量未超过输入预算时：分类摘要和正式结构化抽取都一次读取整份来文，避免无意义分块；结构化条目通过逐字原文引用反查来源附件。
3. 超过预算时：按 Markdown 结构切块，目标块大小为输入预算的约 2/3，并保留 10% 重叠；先生成临时内容提要，再分层压缩为来文级主分类、抽取分类集合和摘要。
4. 多分类抽取默认只包含主分类；长文分块中置信度不低于 0.8 的主分类及模型明确给出的第二主题会并入最终抽取路由，防止压缩时遗漏少数但明确的业务主题。
5. 正式抽取始终回读原始 Markdown。超长来文按较大重叠块抽取，再按业务身份字段合并无冲突的跨块信息；字段冲突的条目保持独立，全部 evidence 均保留。
6. 任一附件、分块或 schema 失败时文档保持失败，不展示为完整结果。

该流程的压缩只用于路由和汇总，正式业务事实始终以附件原文分块抽取为依据。

### 3.9 来文工具和知识库工具并存

- 来文工具负责业务字段过滤、结构化结果、处理状态和未入库全文。
- 知识库工具负责语义检索、知识问答和知识库文档上下文。
- 来文存入知识库后只保存关联 ID，不复制结构化结果。

## 4. 目标数据结构

### 4.1 `incoming_documents`

一份来文一行。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | Integer | 数据库主键 |
| `incoming_id` | String(64) | DocMind 文档 ID，唯一 |
| `source_system` | String(64) | 来源系统，必填 |
| `source_function_id` | String(128) | 来源功能，必填 |
| `source_document_id` | String(256) | 来源文档 ID，必填 |
| `document_metadata` | JSONB | 全部可选业务元数据，非空对象 |
| `status` | String(32) | 文档级处理状态 |
| `ai_classification` | String(128) | AI 原始分类 |
| `classification_confidence` | Float | AI 分类置信度 |
| `classification_evidence` | Text | 支持 AI 主分类的逐字原文依据 |
| `additional_classifications` | JSONB | 附加分类名称、独立置信度和逐字原文依据 |
| `confirmed_classification` | String(128) | 人工纠偏分类 |
| `review_status` | String(32) | `draft/confirmed` |
| `summary` | Text | 基于全部附件生成、用于回答“这份来文整体讲了什么”的文档级摘要 |
| `processing_error` | Text | 文档级处理错误 |
| `knowledge_import_status` | String(32) | 来文入库聚合状态：`none/importing/partial/indexed/failed` |
| `knowledge_import_task_id` | String(64) | 批量入库任务 ID |
| `knowledge_import_error` | Text | 入库错误 |
| `linked_kb_id` | String(80) | 目标知识库 ID |
| `confirmed_by` | String(64) | 确认人 |
| `confirmed_at` | DateTime | 确认时间 |
| `created_by/updated_by` | String(64) | 操作人 |
| `created_at/updated_at` | DateTime | 审计时间 |

约束：

```text
UNIQUE(source_system, source_function_id, source_document_id)
```

文档级状态：

```text
uploaded → parsing → extracting → ready
                         └──────→ failed
```

不引入 `partial_failed`。任一附件解析失败时文档进入 `failed`，管理员修复或重试后再产生完整文档级结果，避免界面把不完整结果误当成完成。

### 4.2 `incoming_document_files`

主文件和附件一文件一行。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | Integer | 数据库主键 |
| `incoming_file_id` | String(64) | DocMind 文件 ID，唯一 |
| `incoming_id` | String(64) | 关联 `incoming_documents.incoming_id` |
| `source_file_id` | String(512) | 来源文件 ID |
| `source_url` | String(2048) | 来源下载地址，可空 |
| `filename` | String(512) | 文件名 |
| `is_main_file` | Boolean | 是否主文件 |
| `content_hash` | String(128) | 内容哈希 |
| `file_size` | BigInteger | 文件大小 |
| `mime_type` | String(255) | MIME 类型 |
| `original_file_url` | String(1024) | MinIO 原文件地址 |
| `markdown_file_url` | String(1024) | MinIO Markdown 地址 |
| `status` | String(32) | 文件解析状态 |
| `processing_error` | Text | 文件处理错误 |
| `linked_file_id` | String(64) | 入知识库后的文件 ID |
| `knowledge_import_status` | String(32) | 单文件入库状态 |
| `knowledge_import_error` | Text | 单文件入库错误 |
| `created_at/updated_at` | DateTime | 审计时间 |

约束：

```text
UNIQUE(incoming_id, source_file_id)
UNIQUE INDEX(incoming_id) WHERE is_main_file=true
```

数据库保证同一来文最多一个主文件；service 保证文档创建完成后至少一个主文件。第一版不固化附件级分类、摘要和结构化结果；超长分析的内容提要仅为任务中间结果，避免产生多套互相冲突的业务结论。

### 4.3 正式业务抽取结果

保留现有 `document_business_extraction_runs/results/items` 三层结构，但调整为文档级语义：

- `incoming_id` 关联文档，不再关联单个附件。
- `DocumentBusinessExtractionResult` 一次 run 只有一个文档级结果。
- `DocumentBusinessExtractionItem` 一行表示一条正式业务事实；`data` 保留 schema 字段和 `source_quote`。
- `evidence` 保存该事实来自哪些附件、原文引用和分块位置。
- API 层按 `item_type` 把多个事实归并为结果组，并生成展示摘要；不把展示模型反写进数据库。
- 删除第一版不用的 `confirmed_data/status/confirmed_by/confirmed_at` item 审核字段。
- 删除 item 级独立 `source_quote` 列；引用保留在 `data.source_quote` 和 evidence 中。

结果组结构：

```json
{
  "item_type": "risk_item",
  "summary": "该来文涉及现场作业、防汛和设备巡检三类风险。",
  "details": [
    {
      "data": {
        "risk_name": "现场作业监护不足",
        "risk_type": "安全管理",
        "management_requirement": "加强现场监护和作业前确认"
      },
      "evidence": [
        {
          "source_file_id": "attachment-1",
          "file_name": "安全检查附件.docx",
          "quote": "各单位应加强现场作业监护……",
          "source_location": "风险事项 / 第 2 条"
        }
      ]
    }
  ]
}
```

`classification` 表示一份来文的单一主分类；正式抽取分类集合由主分类和满足置信度、原文证据要求的附加分类即时派生；`item_type` 表示最终业务结果类型。页面中的“一类一卡”指一个 `item_type` 一张结果卡，不把多个主分类混为一谈。

### 4.4 有效结果选择

```text
effective_classification = confirmed_classification || ai_classification
effective_business_result = latest successful document-level run
```

`effective_*` 为 service 层计算结果，不重复存储。

## 5. 目标接口契约

### 5.1 上传来文

```text
POST /api/incoming-documents/ingest
Content-Type: multipart/form-data
```

字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `source_system` | 是 | 来源系统 |
| `source_function_id` | 是 | 来源功能 |
| `source_doc_id` | 是 | 来源文档 ID |
| `document_metadata` | 是 | JSON 对象，可为空对象 `{}` |
| `files` | 是 | 重复 multipart 文件字段 |
| `file_metas` | 是 | 与 files 顺序一致的 JSON 数组 |

`document_metadata`：

```json
{
  "document_number": "国能办〔2026〕12号",
  "title": "关于开展专项检查的通知",
  "incoming_type": "通知",
  "source_unit": "集团公司",
  "incoming_date": "2026-07-17",
  "urgency": "紧急"
}
```

`file_metas`：

```json
[
  {
    "source_file_id": "main-001",
    "filename": "主文件.pdf",
    "is_main_file": true
  },
  {
    "source_file_id": "attachment-001",
    "filename": "检查清单.xlsx",
    "is_main_file": false
  }
]
```

请求校验：

- `document_metadata` 必须是 JSON 对象。
- `incoming_date` 存在时必须是 `YYYY-MM-DD`。
- `file_metas` 数量必须与 `files` 一致。
- 同一请求最多一个主文件。
- 同一请求不能重复 `source_file_id`。

上传和幂等语义：

1. 同一文档身份可分多次增量上传附件，未出现在本次请求中的既有附件不删除。
2. 新文档首次上传没有显式主文件时，将本次第一个文件设为主文件。
3. 已有文档增量上传没有显式主文件时，保留原主文件。
4. 后续显式上传新主文件时，原主文件改为附件。
5. 同一 `source_file_id` 且内容哈希一致时幂等返回，不重复解析。
6. 同一 `source_file_id` 内容变化或新增附件时，更新文件并把文档结果重置为待处理、待确认。
7. 本阶段不实现删除附件和来文版本历史。

返回：

```json
{
  "incomingId": "inc_xxx",
  "taskId": "task_xxx",
  "status": "accepted",
  "fileCount": 2
}
```

### 5.2 文档级详情

```text
GET /api/incoming-documents/{incoming_id}
```

核心返回：

```json
{
  "incomingId": "inc_xxx",
  "documentMetadata": {},
  "status": "ready",
  "aiClassification": "风险管理类",
  "confirmedClassification": null,
  "effectiveClassification": "风险管理类",
  "reviewStatus": "draft",
  "summary": "……",
  "files": [],
  "businessExtraction": {
    "runId": "ber_xxx",
    "groups": []
  }
}
```

`files` 默认只返回附件身份和处理状态，不返回 Markdown 内容或路径；只有在按需读取接口中明确指定附件后，才返回该附件的 `markdown_path`。

### 5.3 分类选项

```text
GET /api/incoming-documents/options
```

返回后端 `DocumentCategoryResult` 和 extraction schema 的显示元数据，供分类纠偏、筛选和结果展示复用。前端不维护分类映射。

### 5.4 分类纠偏

```text
PUT /api/incoming-documents/{incoming_id}/classification
```

```json
{
  "classification": "考评类"
}
```

行为：

1. 校验分类属于系统配置。
2. 保存 `confirmed_classification`。
3. 将 `review_status` 重置为 `draft`。
4. 使用全部附件 Markdown 和新分类重新执行正式业务抽取。
5. 不覆盖 AI 原始分类和旧抽取 run。

### 5.5 确认结果

```text
POST /api/incoming-documents/{incoming_id}/confirm
```

前置条件：文档状态为 `ready`，有效分类对应的正式抽取 run 成功。

行为：设置 `review_status=confirmed`、`confirmed_by` 和 `confirmed_at`。不修改 item 数据。

### 5.6 存入知识库

```text
POST /api/incoming-documents/{incoming_id}/knowledge-import
```

默认导入全部附件：

```json
{
  "kbId": "kb_xxx",
  "parentId": null,
  "params": {}
}
```

只导入指定附件：

```json
{
  "kbId": "kb_xxx",
  "sourceFileIds": ["main-001", "attachment-002"],
  "params": {}
}
```

固定行为：

1. `sourceFileIds` 省略时表示全部附件；显式传入时必须至少包含一个属于该来文的附件 ID。
2. 已在同一知识库入库的附件自动跳过；可先部分入库，后续补齐剩余附件。
3. 单文件保存 `linked_file_id` 和入库状态；来文根据全部附件状态聚合为 `partial` 或 `indexed`。
4. 已有附件入库后，不允许把同一来文的其他附件导入另一个知识库，也不允许静默替换来文内容。
5. 当前版本不以 `review_status=confirmed` 作为入库阻断条件；“人工确认后才入库”规则留待单独决策，不在本轮调整。
6. 服务重启会把中断的来文处理或附件入库任务标记为失败；已完成部分保留 `partial`，避免页面永久停留在处理中。

- [x] 没有客户正式模板时不创建 assets。

本地模型约束：`incoming-document` 按单篇解读、列表检索和统计分支执行；两个材料生成 Skill 采用 50 条分页、累计数量判断、空结果短路和大结果集确认。三个 Skill 均要求一次一个工具、返回后检查、真实 ID 后置读取，且只在 evidence 提供真实 `source_file_id` 时读取对应原文，不依赖模型自行发现隐含条件。材料生成 Skill 直接声明所需来文工具；文档导出复用 `document-exporter` MCP，工具只在对应 Skill 激活后加载。

### Phase 3 验收标准

1. `incoming-document` 与两个材料生成 Skill 的触发边界清晰，单篇解读不使用重复 Skill。
2. 输出只使用工具返回或原文读取到的事实。
3. 单篇解读覆盖全部附件。
4. 风险台账和考评奖惩汇总的统计与数据库结果一致。
5. 每项结论可追溯到来文、附件和引用。
6. 生成的 Markdown、DOCX 和 XLSX 可预览或下载。

## 13. 总体验收标准

1. 数据库中一份来文只有一条 `incoming_documents` 记录。
2. 每个主文件或附件只有一条 `incoming_document_files` 记录。
3. 所有可选业务字段只存在于 `document_metadata`，不存在双写。
4. 文档级分类、摘要和抽取会读取全部附件 Markdown。
5. 正式结果每个 `item_type` 只有一个结果组，包含 summary 和 details。
6. 页面默认一类一卡、展示一条 detail，其余 detail 可折叠查看。
7. 分类纠偏只能选择系统配置分类，纠偏后重跑正式抽取。
8. 人工确认以整份文档为单位，不提供 detail 级审批。
9. 查询工具支持来文时间、分类、条目类型和关键词。
10. 统计工具输出准确文档数和 detail 数。
11. 全文读取只返回可供 `read_file` 使用的 `markdown_path`。
12. `incoming-document` 和两个首批材料生成 Skill 能基于真实来文生成可追溯回答和材料文件。
13. Phase 4 接入组织用户权限后，未授权用户不能执行超出可见范围的来文搜索、读取和统计。
14. 来文存入知识库前后均可使用来文工具，知识库工具行为不受破坏。
