# 上游 Yuxi 增量同步方案

## 1. 背景

当前 `feature/docMind-dev-v1.0` 从 `xerrors/Yuxi` 演进而来，但已经形成大量 DocMind 专属能力。上游 `main` 同期也持续增加功能和修复，因此本次同步不能把“Git 冲突已解决”作为完成标准，而要逐项判断功能语义、实现质量和对现有定制链路的影响。

本方案以 2026-07-28 刷新的以下提交为可复现基线：

- 共同祖先：`e993f373125bea8dff65f170d20b6fa389c18c2b`
- DocMind：`a116c124`（`feature/docMind-dev-v1.0`）
- 上游 Yuxi：`2f8fa7fd`（`upstream/main`）

同步期间先固定上游基线；完成一轮后再单独评估基线之后的新提交，避免同步目标持续移动。

## 2. 目标与验收标准

### 目标

1. 以 changelog、提交和代码三层证据识别上游新增、单边修改和双边修改。
2. 对上游独有且与 DocMind 定制无冲突的修改，按功能批次同步。
3. 对两边同时修改的能力，比较完整性、正确性、本地模型适配、测试覆盖和维护成本后选择实现，不机械保留任一侧。
4. 保留 DocMind 的来文管理、`chat-iframe`、离线可视化和面向本地模型的上下文治理能力。
5. 每个批次独立检查、测试、Lint，并同步 changelog；高风险主链路还要执行对应集成或 E2E 验证。

### 完成标准

- [ ] 所有上游 changelog 条目均有“同步、已有等价实现、保留 DocMind 实现、暂缓或不适用”结论。
- [ ] 每个“同步”结论能追溯到上游提交和本项目修改。
- [ ] 每个“保留 DocMind 实现”结论记录两种实现的比较依据。
- [ ] 不因同步回退来文、iframe、上下文恢复、交付物或本地模型工具调用能力。
- [ ] 部署、环境变量、接口、数据模型和正式文档随代码同步更新。
- [ ] 相关单元、集成、E2E 和前端测试通过。

上游已经进入 `v0.7.2`，主要增量：

## 4. 初始分类

以下是功能域级别的初始结论，具体结论仍要在对应批次中核对代码和测试。

| 分类 | 功能域 | 初始处理原则 |
| --- | --- | --- |
| DocMind 专属 | 来文管理、业务结构化抽取、`chat-iframe`、离线可视化 | 作为受保护能力，不被上游通用实现覆盖 |
| 双边修改 | AgentRun/SSE、子智能体、上下文压缩、模型参数、附件、知识库工具、认证/CORS/沙箱 | 比较语义后人工整合，禁止整文件覆盖 |

## 5. 实现优劣判断规则

双边修改不按提交时间或代码量决定，统一按以下顺序判断：

1. **行为正确性**：能否覆盖真实问题和失败边界。
2. **DocMind 约束**：是否兼容本地 Qwen 模型、来文、iframe 和当前部署方式。
3. **架构边界**：是否符合 service/repository/router、middleware/toolkit 和前端 API 分层。
4. **数据与安全**：是否引入不可逆迁移、跨用户泄露、路径逃逸或凭据回退。
5. **测试证据**：是否有能证明核心行为的单元、集成或 E2E 测试。
6. **维护成本**：在行为相当时选择职责更清晰、依赖更少、调用链更直接的实现。

如果两边各自解决了不同子问题，不二选一，改为在一个稳定边界中组合，并补充覆盖组合行为的测试。

## 6. 分批同步策略

### 批次 0：基线与审计

- 固定本轮上游提交。
- 建立 changelog 条目和上游提交的映射。
- 记录当前 Docker 服务、基础单测和前端测试状态。
- 仅做盘点，不改变运行行为。

### 批次 1：低耦合正确性修复

候选包括 PDF 页树校验、语义分块空标题、图谱查询/删除边界、异步解析阻塞和独立测试清理。每项仍需确认当前实现没有等价修复。

验收：

- 最小回归测试先失败或证明旧行为缺失，再同步实现。
- 只修改该问题的实现与测试，不带入同提交中的格式化或无关 UI。

### 批次 2：部署、安全与依赖

逐项比较沙箱网络隔离、Provisioner Token、生产凭据、CORS、API Key、Dashboard 权限、MinIO 代理、镜像权限和锁文件更新。

验收：

- `.env.template`、Compose、初始化脚本和部署文档一致。
- 不破坏 `chat-iframe` 的受控跨域、外部换票和 iframe/API 地址推导。
- 数据库迁移前明确列出数据影响和升级步骤。

### 批次 3：知识库、解析与 CLI

同步适用的文件名搜索、external API、CLI 查询、原文件下载、OCR Options、评估断点续跑和图谱恢复能力。

验收：

- 权限以当前用户可见知识库为边界。
- 只读连接器和 Milvus 的能力差异明确。
- 文件下载继续遵守沙箱虚拟路径与真实路径隔离。
- 来文入库复用的知识库服务不回退。

### 批次 4：模型配置与通用前端

比较模型请求参数、provider 映射、模型参考信息、HTML 预览 Skill 和通用交互优化。

验收：

- 模型请求参数保持供应商协议差异，不伪装成通用思考开关。
- 不削弱 DocMind 已有本地模型上下文窗口、Token 准入和首个可见事件行为。
- 前端 API 仍集中在 `web/src/apis`，样式复用现有变量。

### 批次 5：Agent 请求队列与工具审批

这是独立的大功能批次。先移植持久化状态机和服务端不变量，再接主站前端，最后评估 `chat-iframe` 是否需要相同入口。

验收：

- FIFO、幂等、取消、失败暂停、resume、Steer 和 worker 重启恢复有独立测试。
- 审批模式固化到 run，并正确继承到 resume 和子智能体。
- 与 DocMind 的精简 SSE、上下文压缩状态、产物归属和 iframe 线程补拉兼容。

### 批次 6：上下文与运行主链路收口

最后处理 Summary、Token usage、AgentRun/SSE、附件和子智能体中的双边修改。DocMind 自有的预算驱动上下文治理作为当前基线，上游只移植经验证的独立修复或更优边界。

验收：

- 本地模型长对话、工具调用、上下文溢出和历史恢复真实验收通过。
- 私有摘要不进入用户消息流。
- 来文摘要、结构化信息、页面上下文和附件共享预算，不发生尾部静默截断。
- 主站和 `chat-iframe` 的工具状态、Todo、交付物和最终消息一致。

## 7. 每批工作流

每个批次都遵循：

1. 列出上游提交、文件和 changelog 条目。
2. 检查当前代码是否已有等价或更优实现。
3. 先补或选定能证明行为的测试。
4. 仅移植该功能所需代码，不整文件覆盖，不顺带格式化。
5. 执行最小测试、相关层级回归、Lint；主链路再执行 E2E。
6. 更新本方案 checklist 和 `docs/develop-guides/changelog.md`。
7. 当前批次验证完成后再开始下一批。

## 8. 待确认或后置决策

- 上游版本号和发布标签不直接覆盖 DocMind；本轮完成后再决定 DocMind 对外版本号。
- 上游 README 品牌、求职信息和 Yuxi 专属发布内容默认不引入。
- 涉及生产凭据、API Key 数据清理和沙箱重建的破坏性变更，在进入批次 2 前单独列出升级影响。
- 上游沙箱隔离会新增 provisioner token、为每个线程创建独立网络并重建连接到旧共享网络的沙箱；实施前需确认远程环境可以接受现有沙箱会话失效，以及基础设施端口是否允许默认收敛到宿主机回环地址。
- `chat-iframe` 是否暴露“请求排队/Steer/工具审批”交互，在批次 5 根据嵌入场景再决定；后端协议不得默认把主站 UI 选择强加给外部系统。
