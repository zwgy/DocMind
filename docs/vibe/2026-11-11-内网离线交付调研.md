# docMind 内网离线交付调研

日期：2026-11-11。源码检查基线：`97dd5543`。本记录保留最初调研和方案推演；实施后的操作以[内网离线部署](../advanced/offline-deployment.md)为准，验证进度见[实施计划](2026-11-11-离线交付实施计划.md)。不将开发环境验证视为目标机离线验收。

## 推荐部署方式（按最新澄清收敛）

采用“联网侧一次打包，测试/生产使用同一镜像包，各自维护运行配置”。交付端只使用 Docker Compose，不要求安装 Python、Node 或构建工具。延用现有生产 Compose 结构，不另起部署框架。

```text
联网构建机：选定主线提交 → 构建并放入离线资源 → 断网验收 → 导出版本包
                                                     ↓ U盘
目标机：解压到 /data/2/docmind → 填写环境配置 → 导入镜像并启动 → 验收
```

部署脚本按以下接口落实；是否可发布以实施计划的实际验证记录为准：

```bash
# 联网侧：从确定提交生成一个包含所有运行镜像的交付目录/压缩包
bash scripts/package-offline.sh <release>

# 内网侧：首次生成本机配置，填写模型地址、密钥及访问端口后安装
bash deploy.sh init
bash deploy.sh install

# 日常只需状态、日志、重启；升级时使用新版离线包和原运行配置
bash deploy.sh status
bash deploy.sh logs
bash deploy.sh restart
```

只补一个打包入口和一个部署入口，复用现有初始化与 Compose 命令；不引入镜像仓库、安装平台或新的服务。交付包内生成一份最终 `compose.yaml`：固定成品镜像标签，移除构建定义，明确 provisioner/runtime 镜像引用；无需部署人员手工合并多份 Compose 文件。`install` 负责校验包、导入镜像、以 `--no-build --pull never` 启动和检查状态，不删除数据卷，不覆盖已有环境配置。其下层命令就是 `docker load` 与原生 `docker compose`。

测试和生产使用同一发布标签及服务结构，仅运行配置（模型地址/Key、端口、实例标识、密码等）不同，数据相互隔离。在同一机器并存时还须不同目录、项目/网络名和容器名、端口；可交付时将 Compose 固定容器名改为由项目名管理，避免两套环境冲突。初期不增加独立的测试功能分支或另一套镜像构建逻辑。

内置 OCR 现在确实需要三个 ONNX 模型：文字检测、方向分类和文字识别。Python 依赖已安装不等于权重已准备。离线包构建时把约 21 MB 模型及分句资源直接写入 API 镜像即可；部署人员无需另拷模型目录，不依赖内网的聊天或嵌入模型来做 OCR，也不需要 GPU。

实施验收只保留五项：所有核心服务就绪；真实聊天回复；沙盒命令与产物；扫描 PDF OCR→入库→检索；重启后的配置/数据持久化及定时任务触发。打包前在无外网且无历史模型缓存的环境验证，目标 CentOS 7 主机再做同一套核心验证。

以下是源码调研和原生命令细节，用于后续实现依据；交付给部署人员时以短版 `DEPLOY.md` 和上述两个入口为准。

## 1. 目标条件

用户提供截图：CentOS Linux 7 (Core)，内核 `3.10.0-957.el7.x86_64`；双路 Intel Xeon Gold 6230，每路 20 个物理核心、每核 2 线程，共 40 个物理核心、80 个逻辑 CPU，具有 AVX2。内存页面为 251.2 GB、当时已用 204.9 GB。最新终端输出显示根分区 50 GB、使用率 100%、只剩约 16 MB；`/data/2` 容量约 1.9 TB，已用 253 GB、可用约 1.6 TB。后续项目部署在 `/data/2/`。这些都是截图时点事实，不代替安装当日检查。

用户确认 Docker 28.2.2 已安装，内网能够通过 Base URL / API Key 访问大模型、嵌入模型等。因此采用 `linux/amd64` 运行镜像、内置 CPU RapidOCR，不打包大模型/嵌入模型权重、不启动 MinerU/PaddleX 的 GPU profile。部署配置只填写实际模型地址、凭据、模型 ID 与向量维度；rerank 接口仅在启用重排时需要。

建议项目根目录 `/data/2/docmind`，业务数据由现有相对挂载落到 `/data/2/docmind/docker/volumes/`。最新截图已确认 `DockerRootDir=/data/1/docker_data`、驱动 `overlay2`，因此无需为了本项目迁移 Docker 数据目录；镜像及容器层使用 `/data/1`，项目文件和挂载数据使用 `/data/2`。仍需核对 `/data/1/docker_data` 所在分区的剩余空间。根分区已经满，即便 Docker 位于数据盘，也应在安装前由运维处理根分区空间，避免系统日志和临时文件写入失败。

CentOS 7 的旧内核与已安装的新 Docker、当前应用镜像组合仍需实测；容器共享宿主内核，Docker 已安装不能证明 Python/Node、Milvus 和沙盒都可正常运行。检查 CPU 指令集、Docker 存储驱动、文件系统及 Compose 插件，先做一轮目标环境冷启动验收。

## 2. 已有脚本及缺口

| 文件 | 当前职责 | 离线交付缺口 |
| --- | --- | --- |
| `docker/save_docker_images.sh` | 拉取固定清单并 docker save | 主要是基础镜像，缺应用成品镜像、Postgres、Redis、provisioner、动态沙盒；Bash 数组镜像字符串后带逗号，逗号会成为镜像名的一部分 |
| `docker/save_docker_images.ps1` | Windows 侧同类导出 | 同样清单不完整，Python 仍为 3.11，与当前后端 3.12 不一致 |
| `scripts/manage.sh` / `.ps1` | 初始化、构建、启动等 | `prod deploy` 固定包含 `--build`，无法作为内网离线安装命令；`start` 不构建，但仍需完整镜像和配置 |
| `docs/intro/quick-start.md` | 简单介绍 save/load | 已提示清单可能陈旧，没有覆盖运行资源、完整交付目录和断网验收 |
| `docker-compose.prod.yml` | 生产服务编排 | provisioner 只有 build、没有固定 image；动态沙盒默认仍指向外部基础镜像，和开发环境的项目 runtime 不一致 |

结论：已有镜像备份入口，没有可直接用于本次交付的完整离线打包/安装流程。无需重写部署框架，补齐当前脚本的运行镜像清单、生产镜像引用及离线启动路径即可。

## 3. 交付物

CPU 核心部署共 15 个常驻服务，复用后端镜像后是 10 类静态运行镜像，加动态沙盒 runtime 共 11 类：

- 项目镜像：`yuxi-api`、`yuxi-web`、`yuxi-chat-iframe`、`yuxi-sandbox-provisioner`、`yuxi-sandbox-runtime`。
- 基础设施运行镜像：`postgres:16`、`redis:7-alpine`、`neo4j:5.26`、`quay.io/coreos/etcd:v3.5.5`、`minio/minio:RELEASE.2023-03-20T20-16-18Z`、`milvusdb/milvus:v2.5.6`。

构建器使用的 Go、Node、Python 等基础镜像无需另外导入目标机，只需保存完整的最终运行镜像；docker save 会包含其所需的父层。动态沙盒不在默认 Compose 服务清单中，必须额外保存。

建议交付目录：

```text
docmind-offline-<release>/
  images.tar
  images.txt                    # 精确镜像名/标签
  image-manifest.json           # 镜像 ID、平台与源码提交
  SHA256SUMS                    # U盘拷贝前后核验
  docker-compose.prod.yml
  docker-compose.offline.yml     # 待补：固定 provisioner 镜像
  .env.template
  scripts/manage.sh
  docker/sandbox_provisioner/sandbox.env
  DEPLOY.md
```

初始化从模板在目标机生成独立 `.env.prod`；不要复制开发机 `.env`、数据库、业务文件或凭据。此方案默认新部署，迁移历史知识库/账号/业务配置是另一项数据迁移工作；docker save 不包含数据卷和容器可写层。

### OCR 和其他离线资源

RapidOCR 的检测、方向分类、识别三个 ONNX 模型合计约 21 MB。已验证过的开发容器把它们下载在 `site-packages/rapidocr/models`，不在原镜像层中；直接 docker save 原镜像不会带走这些下载结果。正式交付应在构建阶段完成模型下载，把它们写入后端成品镜像。

语义分块使用 `nltk` 的 `punkt_tab`，当前后端 Dockerfile 未准备该资源。将它一并写进镜像的 `/usr/local/share/nltk_data`。其他实际启用的解析器、Skills/MCP 也须按所需能力检查运行依赖；云搜索、云图片生成和远程 Skills 安装不能在隔离网络里自动获得外网能力。

前端主体由 Nginx 本地托管，但仍存在外网图片资源：`web/src/utils/modelIcon.js`、`kb_utils.js` 的品牌图标以及 `pixelAvatar.js` 的头像 URL。它们不等于聊天接口不可用，但完整离线展示需将必要图标本地化，并验证已有头像替代显示。首页 GitHub 信息和外部帮助链接不计作内网可用功能。

## 4. 联网侧打包顺序

以下是拟采用的 Linux/Bash 操作路径，镜像标签以选定发布提交为准。应在有足够空间的联网构建机执行，平台为 `linux/amd64`。所有镜像均须从同一选定源码重新构建，不能直接保存依赖源码挂载运行的旧开发镜像。

1. 从最新主线选择确定提交，生成干净源码副本；固定 `YUXI_VERSION` 为唯一发布标签，记录 Git 提交。目标分支后续变化不应影响已交付标签。
2. 构建后端、Web、iframe、provisioner 和项目 sandbox-runtime。联网侧安装全部 Python/Node/系统依赖，内网侧不执行构建。
3. 在后端最终镜像中预热 RapidOCR，下载 punkt_tab。可在联网构建后增加以下薄镜像层；此处是示例，尚未落地为仓库脚本：

```dockerfile
FROM yuxi-api:offline-base
RUN python -c "from yuxi.knowledge.parser.rapid_ocr import RapidOCRParser; h = RapidOCRParser().check_health(); assert h['status'] == 'healthy', h"
RUN python -m nltk.downloader -d /usr/local/share/nltk_data punkt_tab
```

用 Dockerfile 形成镜像层，不依赖 `docker commit` 当前业务容器。前端和沙盒同样只携带预安装的运行依赖。

4. 拉取六个基础设施镜像，准备精确清单。以标签 `offline-<commit>` 为例，清单中的项目镜像均必须已真实构建：

```text
yuxi-api:offline-<commit>
yuxi-web:offline-<commit>
yuxi-chat-iframe:offline-<commit>
yuxi-sandbox-provisioner:offline-<commit>
yuxi-sandbox-runtime:offline-<commit>
postgres:16
redis:7-alpine
neo4j:5.26
quay.io/coreos/etcd:v3.5.5
minio/minio:RELEASE.2023-03-20T20-16-18Z
milvusdb/milvus:v2.5.6
```

`<commit>` 是占位符，交付前必须换成实际发布标识；核对每个镜像架构和 ID，再执行：

```bash
mapfile -t images < images.txt
docker image inspect "${images[@]}" > image-manifest.json
docker image save -o images.tar "${images[@]}"
sha256sum images.tar images.txt image-manifest.json docker-compose.prod.yml docker-compose.offline.yml > SHA256SUMS
```

5. 在全新数据目录和独立项目中用导出的镜像做一次断网冷启动，确保本地无缓存依赖，且仍能访问指定内网模型服务。核心容器禁止构建/拉取，动态沙盒也须验证本地镜像存在。先完成这一轮，再拷 U 盘。U 盘使用支持超过 4 GB 单文件的文件系统，例如 exFAT；目标电脑也需有对应读取能力。不要假定 FAT32 能容纳整个 tar 包。

生产离线覆盖文件只需为 provisioner 指定固定成品镜像，例如：

```yaml
services:
  sandbox-provisioner:
    image: yuxi-sandbox-provisioner:${YUXI_VERSION}
```

`.env.prod` 同时设置 `SANDBOX_IMAGE=yuxi-sandbox-runtime:<实际发布标识>`，使沙盒使用带预装依赖的项目 runtime。其它应用镜像通过生产 Compose 已有的 `YUXI_VERSION` 使用一致标签。

## 5. 目标机安装顺序

先在内网主机运行只读命令，确认安装位置、Compose 和镜像存储目录：

```bash
uname -r
uname -m
docker version
docker compose version
docker info --format 'DockerRootDir={{.DockerRootDir}} Driver={{.Driver}}'
df -h / /data/2
free -h
lscpu
```

将交付目录拷到 `/data/2/docmind`。确认镜像存储空间足够，且目标机没有与生产文件中 `postgres`、`redis`、`minio` 等固定容器名或 80/5432 端口冲突的现有服务。项目名前缀不能解决显式 `container_name` 冲突，遇到冲突应在交付配置中明确改名/改端口，不关闭其他项目。

交付包补齐并通过冷启动验证后，目标机命令为：

```bash
cd /data/2/docmind
sha256sum -c SHA256SUMS
docker load -i images.tar
bash scripts/manage.sh prod init
```

按该主机修改 `.env.prod`：`YUXI_VERSION`、项目 runtime 的 `SANDBOX_IMAGE`、内部模型凭据环境变量、实际访问地址/来源、必要端口。`SANDBOX_DOCKER_THREADS_HOST_PATH` 如显式填写应为 `/data/2/docmind/docker/volumes/yuxi/threads`，不可沿用开发机路径；provisioner 也支持从自身挂载检测该路径。

随后只解析和启动已有镜像：

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml -f docker-compose.offline.yml config --quiet
docker compose --env-file .env.prod -f docker-compose.prod.yml -f docker-compose.offline.yml up -d --no-build --pull never
docker compose --env-file .env.prod -f docker-compose.prod.yml -f docker-compose.offline.yml ps
curl -f http://127.0.0.1/api/system/health
```

不运行 `prod deploy`，不启用 `--profile all`。初始化管理员后，在“系统设置 → 模型配置”配置并启用实际内网对话模型、embedding 模型和准确向量维度；通过管理界面/接口将系统默认 OCR 设置为 `rapid_ocr`。API 容器须能访问模型地址，Base URL 不能误填目标容器内部的 `localhost`。

交付包内已包括镜像，不需要在内网重新安装 Python、Node、pnpm、Go 或执行 pip/npm；目标机已具备 Docker，还需可用的 Compose v2 插件。若缺少插件，只补与 x86_64、现有系统适配的离线插件，不盲目升级整个 Docker 服务。

## 6. 验收与未决事项

- 新目录首次启动，确认数据库/对象存储/向量库和所有核心服务就绪；不只看 API 健康接口。
- 验证内网模型真实回复，执行一次沙盒命令并核验文件产物，确认没有临时拉取沙盒镜像。
- 上传中文扫描图、无文字层 PDF，经 RapidOCR、MinIO、分块、embedding 到 Milvus 入库，检索结果和原文来源一致；任务通知真实到点触发。
- 重启服务并再次访问，验证配置与数据持久化；使用无外网、无浏览器缓存的客户端确认页面和嵌入助手。
- 保留镜像 ID、平台、提交号、校验和、安装命令及失败日志作为交付记录。不能把联网预热通过表述成目标 CentOS 7 已验证。

尚待确认：`docker compose version` 的实际插件版本（截图执行的是 `docker compose --version`，输出 Docker 引擎版本，不能据此确认插件版本）、`/data/1/docker_data` 所在分区余量、现有容器与端口冲突；具体模型 ID/向量维度及容器到内网模型服务连通性。API Key 不应贴在调研记录或聊天中。
